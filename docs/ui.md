# Zinko UI

## Direction

Zinko should feel like a professional debugging tool: dense, calm and fast, in the spirit of Linear and Sentry, not a marketing dashboard. Consultants live in it, and their clients see only the polished report.

- Dark and light themes, with light as the default for reports.
- Logo-tinted neutrals (hue 285) with violet `primary` as the only brand accent; `sidebar` supplies the navigation surface. Severity uses `sev-critical` (red), `sev-warning` (amber), `sev-info` (blue); passes use `status-pass` (green). Each set has plain text/glyph, `-bg`, `-border` and `-solid` tokens; status uses the same four-token set (`status-pass`, `status-active` for running, `status-neutral` for finished, queued, not audited and unknown) so a badge is `border-<set>-border bg-<set>-bg text-<set>` in both themes. Tints belong in badges, headers and detail views; rows stay neutral. `destructive` is for destructive actions and form errors.
- System sans (`ui-sans-serif, system-ui, -apple-system, "Segoe UI", Roboto, sans-serif`); no Inter download or font dependency. System monospace for IDs, parameters, URLs and timestamps. The type scale is `text-2xs` 11/16, `text-xs` 12/16, `text-sm` 13/20, `text-base` 14/22, `text-lg` 16/24, `text-xl` 20/28 and `text-2xl` 28/34 (px size/line height). Page titles are 20px (28px from `sm`). Base radius is 8px (sm 4, md 6, lg 8, xl 12).
- Meaning uses a glyph and a word: Critical a filled diamond, Warning a filled triangle, Info a filled dot; Fail an x ring, Pass a green check ring, a finished audit a neutral check ring, Partial a half ring, Could not check a neutral dashed ring, Not applicable a dash ring, Queued a hollow ring, Running a violet spinning arc. Could not check is neutral, never amber or green. Reduced motion stops spinning and pulsing indicators.
- Keyboard-first: `⌘K` / `Ctrl+K` command palette (built); `j`/`k` through findings and `e` for the evidence panel are not built.
- Every number links to the evidence behind it.
- Pages are `mx-auto max-w-6xl space-y-6` for lists and full width for audit pages. Status and severity are never colour alone: a glyph (`StatusGlyph`) and a word sit together, so a grayscale screenshot still tells Fail, Could not check and Pass apart.
- Touch targets are at least 32px (buttons `h-8`, tabs `h-8`, icon buttons `size-8`; dense table rows are 28px with a pointer and 36px below `md`). Every interactive element shows a solid focus ring on keyboard focus, including focusable tab panels: `focus-visible:ring-2 focus-visible:ring-ring focus-visible:ring-offset-2 focus-visible:ring-offset-background` (`--ring` is `oklch(0.52 0.19 286)` light and `oklch(0.68 0.16 286)` dark: 4.75 to 5.95:1 on page, card, sidebar, accent, muted and popover in light and 5.02 to 6.56:1 in dark; the offset gap in the page colour keeps it visible on a primary button, 5.45:1 light and 3.87:1 dark against the fill). Where an ancestor clips overflow (scrolling tab bars, table cells, list rows, popovers) the ring is `focus-visible:ring-2 focus-visible:ring-ring focus-visible:ring-inset`. Active and selected states are never a ring: tabs underline (`tabLink` in `lib/row-style.ts`, shared by the audit and settings tab bars), the sidebar item a fill and a 2px left rule, rows a fill and a 2px rule (finding rows on the right edge, because the left carries severity). Colours come from tokens only; the exceptions are the logo mark (`#8b7cf6`) and the `bg-black/50` scrim of dialogs.

## Design principles

1. **Lead with one number and one sentence.** A screen opens with the answer (a score, a count, a state) and one line that says what it means.
2. **A score never claims more than was checked.** Below full coverage the number says so; a bare "100/100" without full coverage is a bug.
3. **Three text sizes do the work.** Page title `text-xl sm:text-2xl font-semibold tracking-tight` (`PageHeader`); section `text-base font-semibold` (`SectionHeading`); label `text-2xs font-medium uppercase tracking-wide text-muted-foreground`. A display size (`text-5xl font-semibold tabular-nums tracking-tight`) is only for the answer.
4. **Surface depth is the hierarchy.** Page (`background`), card (`card` with `shadow-xs ring-1 ring-foreground/5`) and sheet or popover are three token levels; the sidebar is a fourth, slightly darker in light mode. Alerts are inline rows unless they block.
5. **Explain on demand.** One sentence is visible; detail sits in a popover or a disclosure.
6. **Colour is a signal, not decoration.** One primary action per screen. The only gradient is the auth backdrop, built from tokens.
7. **Tables adapt, they do not clip.** They scroll inside their container with scroll edges, or drop columns, never cut a value off.
8. **One vocabulary, one component; an unknown status fails loudly.** A status is a typed union (`AuditStatus`, `RunStatus` in `@repo/core`); `StatusBadge` takes a `BadgeStatus`, so an unmapped value is a type error, and a stored value the app does not know is passed through `toBadgeStatus` and reads "Unknown" in a neutral badge, never the raw string.

## Vocabulary

| Where | Words |
|---|---|
| Severity | Critical, Warning, Info |
| Check result | Fail, Could not check, Pass, Not applicable (the stored word `inconclusive` never appears) |
| Triage | Open, Accepted risk, Fixed |
| Audit | Queued, Running, Finished (neutral: it says the audit ended, not that the site is fine), Partial, Failed, Not audited |
| Run | Queued, Running, Captured (a run that loaded), Partial, Failed |
| An audit without check results | Not evaluated, never shown as clean |

## Navigation

```
Sidebar: organization switcher, Find… (⌘K), Clients, Settings, account menu
├── Clients                       list → client → site
│   └── Site                      history of audits, New audit
│       └── Audit                 header, then tabs Overview · Runs · Findings · Tag matrix · Hits · Report
└── Settings                      Profile · Members · AI · Branding
```

Below `md` the sidebar is a left `Sheet` behind a menu button in a thin top bar and closes on navigation. Each page opens with a `PageHeader` (breadcrumb, title, meta line, actions). Tab order is a "Skip to content" link (visible only on focus), the navigation, then `<main id="main">`, which the link focuses.

## Screens as built

**Shell.** The sidebar opens with the wordmark (mark and "Zinko", home link), then the organization switcher (menu: organizations with a check, Members, Create organization). Items are `h-9`; the current page has `bg-accent`, `font-medium` and a 2px primary rule on its left edge. In light mode the sidebar is a slightly darker surface than the page and cards are white with a hairline ring. The foot row is the account menu: email, Theme (Light, Dark, System, a radio group, stored per browser), Sign out. The landing page keeps its own theme toggle; the sign-in and sign-up pages follow the stored theme.

**Command palette.** `⌘K` / `Ctrl+K` anywhere in `/app`, or the "Find…" row (the only way on touch). Groups: Actions (New client, which asks for a name; All clients; Settings; AI settings; Members; Toggle theme), Recent audits (the newest five, of sites matching the query), Clients and Sites (organization-scoped names from `searchTargets`), New audit (one "New audit for <site>" per matching site, only once something is typed) and Switch organization. Esc closes and focus returns to where it was.

**Clients.** A table (Client, Sites, Last audit with a status badge, a relative date, the score through `ScoreFigure` ("Lowest of 2 sites" over several), Open findings per severity, and "Last five scores", an inline SVG sparkline on a fixed 0 to 100 scale with a hollow dot for any audit that was not fully checked); the page is `max-w-5xl`. The figures come from each site's latest settled, evaluated audit; a running audit shows "Audit running" beside them. "No open findings" appears only at full coverage with nothing that could not be checked; otherwise "0 open · not fully checked", "Not evaluated" or "Not audited". A search box filters by name; "New client" opens a dialog. A fresh organization sees an empty state and a three-step checklist (client, site, audit) that can be dismissed.

**Client and site.** The client page lists its sites (origin in mono, last audit, open findings, audits) and has "Add site"; archive and delete sit in a "…" menu behind a confirm dialog (a client or site with audits can only be archived). The site page has "New audit" in the header and a history table (started, status, runs "9 of 9" with "n runs could not finish", score, findings by severity or "Not evaluated"), Newer and Older. "Add site" takes an address with or without a scheme (`https://` is added) and shows a refused address under the field. A missing client, site or audit shows the app's "not found" page with "Go to clients" (`components/not-found.tsx`). A site address typed without a scheme gets `https://`, or `http://` for localhost and private hosts. "Edit address" in the site's "…" menu changes it: free for a site without audits, and for one with audits only between http:// and https:// (the host and port stay, earlier audits keep the URLs they captured). A failed preflight on an https address says to try http://. The client's "Add site" and the clients list's "New client" appear in the header only when the page is not empty, so an empty page has one action. Score cells say how many runs they come from, and finding counts hide zero severities.

**New audit.** Three numbered sections (1 Pages, 2 Scenarios and viewports, 3 Options, `border-t pt-8`) and an `h-10` Start button: Pages (start URL, key pages with per-line errors and "n of 19"), Scenarios and viewports (checkbox cards with All and Only reject, a Desktop/Mobile toggle), Options (ad-click IDs, journey, and under Advanced, answering tracking requests locally). With journey on, a numbered list shows which pages are walked. A sticky estimate (below `lg` a one-line bar, "12 runs · about 3 minutes" and Start) shows the run count, the breakdown, the duration at 7 s per work unit, and the Start button, disabled with a reason when no scenario or viewport is chosen. Pages must be on the site's origin including its port ("localhost:4400"); another port is refused. The last audit's settings prefill with the line "Settings copied from your last audit" and a Reset to defaults button (a copied start or key page that is no longer on the site is dropped). Each option has a one-line gloss (click IDs, journey, answering tracking requests locally, Global Privacy Control) and a help popover sits beside "Consent scenarios". Start loads the start page once on the server (`preflight` in `server/audits.ts`: redirects followed by hand and kept on the site, private hosts refused outside dev) and a page that cannot be reached, answers 404, 410 or 5xx, or redirects off the site is reported under the Start URL before any audit exists. The time left on a running audit is recalculated from its own pace (`remainingTime`), one figure, never a range.

**Audit and runs.** On every tab except Overview (and while the audit runs) the header is one line: title, status, runs, open findings by severity ("5 open: 4 Critical, 1 Warning", the same count as the Findings tab, accepted and fixed excluded), duration, date, and a pill "n of m runs could not finish · See why" linking to the Runs list. Overview keeps the full header with one summary line under the status ("28 runs: 26 captured, 2 partial, 0 failed", open findings, duration, start time) in place of the old four-column stat strip. A run that loaded is "Captured" (neutral glyph, never a green check: Findings says pass or fail); a matrix cell shows the worst failing severity with its failing-check count, then the hits, and a captured run with 0 hits says no tracking was seen. Pages show as paths without the query, the full URL in a tooltip, and "+ click IDs" when the query carries them. On Findings (lg and up) the list and detail pane fill the viewport and scroll on their own. In the finding detail, "Where it was seen" is a list of two-line rows and empty evidence tabs are hidden; Accept risk says "A reason is required" and the toast offers Undo. The header shows the status, a live dot (Connected / Reconnecting) and either progress (a bar, "12 of 44 runs", elapsed, time left, counts of running, partial and failed) or, when finished, that summary line. While the audit runs, a box names every failed or partial run with its reason; once it finished, Overview carries the one notice (below). Tabs carry counts. A finished audit with at least one evaluated run opens on Overview (an audit with none, or one still running, opens on Runs; a `view` or `run` in the URL is kept); Runs stays one click away and the completion toast's action is "Overview". The Runs tab has three views: a matrix (page rows, scenario columns grouped by viewport, a glyph and the hit count per cell, a hover card with the screenshot), a list and thumbnails. A cell opens the run sheet (`?run=`, a right `Sheet`, a bottom one below `md`): screenshot, facts, reason, the page's other scenarios, previous and next (arrow keys), Open in Hits and the failing findings that cite the run. A toast announces completion once. The one-line header starts with a small back link to the site. Dates are "28 Oct 2026, 02:21" (`shortDateTime`) in the reader's time zone, never the US form; they render in UTC on the server and switch after hydration (`useTimeZone`). While an audit has no run on a capture engine the progress line says "Waiting for a capture slot" and elapsed time does not run until the first run starts. After a route change focus moves to the page's heading (never on first load); the sidebar marks Clients on client, site, audit and new-audit pages; the Find palette input has a focus ring and its recent audits show date, status and score; tables show a soft edge where they scroll sideways.

**Overview** (`/overview`). The score block is about three lines: the number out of 100, a band word and glyph (Critical issues, Needs attention, Minor issues only, No failing checks; never "healthy" or "clean") and "How this is scored"; "Start with <severity> <worst open finding> [Open finding]"; and one status line. When some findings are accepted risks the block adds "42 excluding 1 accepted risk · 28 counting all findings" (the same `healthScore` run on the findings without accepted risks; fixed findings still count). "How this is scored" opens beside the button, limited to the room Radix reports (`--radix-popover-content-available-height`, 16px collision padding) and scrolling inside, and starts with "Starts at 100. Each failing check costs points, more for Critical, more when it fails on more pages.", then the per-rule lines and the sum; a Details disclosure holds the formula, weights, the Critical cap (79), what is not scored, the score version and the rules versions. The purchase-fields caveat appears only when that rule failed. Status lines: "Partly evaluated: 38 of 40 runs have check results" only when some runs have none; "Could not check: 6 rules, on 9 runs" is a disclosure listing the check titles; "All 40 runs evaluated, every check resolved" only when neither applies. When the start page could not be loaded (every run of it failed or left with a Navigation, HttpStatus or Timeout error), when any other key page could not (the alert names it: "Could not load /nope-404/: Page returned 404 (Not Found)") or at least half the runs did not finish, a warning alert "This audit is incomplete" leads the page (it is the only notice about unfinished runs: a finished audit with partial or failed runs but a usable score gets "2 of 28 runs could not finish (2 partial)" in the same place, and the affected runs sit behind a "See which runs" disclosure) and the score reads "Incomplete" in muted type beside the band. A neutral dashed alert "n failing consent checks rest on an undetected banner" (banner detection uncertainty) is the one place that says so, with the affected rules; the findings keep their weight. On Findings the list row says "banner not confirmed on n runs" and the finding's run table marks each affected failing run "Banner not detected" or "Banner status unknown". Mixed rules versions add "mixed rules versions" beside the band and an alert. After the banner alert, the worst open failing finding is shown in full: severity, title, "failed on 16 of 36 runs where it could be checked, across 3 pages and 4 scenarios", why it matters, the fix steps with a copy button, the stored message of the first failing run, and Open finding and Open in Hits (that run). Triaging it promotes the next; with none open the section says "No open failing findings". Counts by area is a table (Critical, Warning, Info, Could not check; compact padding so all columns fit at 390px) of the areas with a failing or could-not-check rule, whose non-zero counts link to Findings with `area` and `severity`; below it "No failures in X, Y: checks ran and passed." lists areas where checks passed and "Nothing was checked in Z (not evaluated or not applicable)." the rest. Tags seen has one link per vendor ("Google Analytics 4: 2 destinations, 3 events") to the Tag matrix. Not evaluated is an `EmptyState`; a running audit says "Available when the audit finishes".

**Report** (`/report`, built so far: cover, summary, scope and method, consent scenarios). A chip "Draft, not shared" and a Branding link (owners and admins; members read "Ask an owner or admin") above the document. The document is `ReportView`, a pure component on `.report-paper` (always light, at most 210mm wide, the agency's accent as a top band and on the agency name): cover (logo, agency, client, site and host, "Audited on 28 October 2026 (UTC)", pages as `Page 1 (start page)`, scenarios, viewports, "Prepared by"), then the summary: the score as `ScoreFigure` (the same two-tier honesty as the Overview: muted "Not fully checked" when runs are missing or did not finish, "n of m checks resolved" otherwise), "excluding accepted risks", the incomplete banner, the arithmetic (first five lines, the sum, the formula and weights) and the honesty lines (Partly evaluated, Unresolved checks, the undetected-banner note), counts, "Generated from the findings" headlines and the worst open finding. Then Scope and method (pages, scenarios with what each does, viewports, run counts, rules and score versions, "mixed rules versions", the undetected-banner note and two fixed sentences: deterministic rules, no model decides; technical behaviour, not legal advice) and Consent scenarios (vendor by scenario; a cell says Fired "n of m runs, x hits", None seen "in n captured runs" or Not captured only when no run of the scenario was captured; "from n partial captures"; for Accept and Reject the hits before and after the choice and "choice observed on k of m runs", or "No choice was observed, so hits are not split"). Running audits say "Available when the audit finishes"; an audit without check results is Not evaluated.

**Report editing.** The toolbar has a Consultant view / Client view toggle and "Page labels: Page 1, Page 2" (or "paths and ad-platform IDs"), which opens a dialog listing exactly what Detailed would print (the entered paths and the Meta and TikTok IDs in the evidence) before the choice is saved. In Consultant view the Summary has Edit summary (a right sheet, 2000 characters, empty goes back to the generated summary; the author's text prints as "Summary by <agency>" above "Generated from the findings") and each finding has Add note, Change owner and Leave out of the detail. A finding left out stays in Consultant view dimmed with a "Left out" chip and its controls, is absent from Client view, the plan and the report model, and is listed by title under Appendix C; the score and counts still include it. Text that looks like an email or phone number saves with a warning. Dialogs open from their own buttons, so focus returns to them.

**Action plan and appendix (report).** The plan groups open findings under "Consent platform admin", "Tag manager or marketing", "Site developer" and last "Owner not assigned" (audits from before owner hints), one line each: severity glyph, the finding (an in-page link) and its first fix step; "Not in the plan" lists accepted risks and fixed findings with their state. The appendix: A Could not check (check title and run count, never presented as a pass), B Not evaluated (runs that did not finish, with a fixed reason), C Left out of the detail, D the full score arithmetic, E the rules of this audit with pass, fail, could-not-check and not-applicable counts, F a legend.

**Findings (report).** Failing findings by severity as cards: badge, area, title, "Failed on n of m runs where it could be checked, across p pages (scenarios)", triage (Accepted risk with its reason; "marked fixed by the author, not re-verified"), why it matters, how to fix it, one evidence table (Source, Event, Destination, Timing, Consent state; Meta and TikTok are "Meta pixel" and "TikTok pixel" without an ID under Standard) or "Evidence is not available for this finding in the stored captures.", the undetected-banner note and the owner ("Owner not assigned" on old audits). The Accept risk dialog says "The reason is printed in client reports."

**Findings.** Coverage is a muted line at full coverage and an alert with a segmented bar when partial or mixed. Tabs Open, Accepted risk and Fixed (counts); severity chips and an Area menu, both in the URL. Failing findings are two-line rows under sticky severity headers with a 2px severity rule; "Could not check (n)" is a collapsible group of neutral rows (dashed glyph, the rule's `checkTitle`, the reason, no severity colour). Each failing row ends with "8 of 26 runs" and a thin proportion bar (inline SVG, the number carries the meaning in grayscale). Selecting a row opens the detail beside the list (`?finding=`), or in a bottom sheet below `lg` with previous and next: severity and rule id, the triage menu (Accept risk asks for a reason in a dialog), why it matters and how to fix it side by side from `xl`, where it was seen (a scrolling list of about three rows), the evidence, then the explanation (a table whose selected row drives the evidence tabs; empty tabs are disabled), Open in Hits per evidence item. Evidence chips are named by what they are ("Hit 1", "Request 2", "dataLayer push 3"; the raw request id is a tooltip) under a line giving the run's page, scenario and viewport. Not evaluated, running and "not confirmed clean" states are distinct from "No findings".

**Tag matrix** (`/matrix`). Rows are tags (vendor name and destination ID in mono; GA4, Google Ads, Meta, TikTok, then others), 25 per page when the columns are scenarios and 10 when they are pages ("Tags 1–25 of 140", Previous and Next, `tagPage` in the URL). Controls: a Viewport toggle (only when the audit ran more than one), By scenario or By page, a Pages select (all pages, each page by its path with the host added only when two audited URLs share a path, a hash route kept as "/#/cart", or "Journey from /shop"; the full URL is the identity, so `https://a.example/shop` and `https://b.example/shop` stay separate) or a Scenario select, all in the URL. A column header gives the label, the run count and, when some runs are partial or not captured, a partial glyph and "3 complete, 1 partial, 1 not captured". Column headers by page show the path only (the full URL in a title) and a "+ click IDs" tag when the audit added test click IDs. Events in a cell follow one order for the tag in every column (most hits in the whole audit first, then name). A cell is a button (32px minimum, focus ring) showing up to 4 event chips with `n/m` runs (a single-run column shows `×hits`) and "+n" for the rest; the row's chevron expands every chip. Cell words: "from 2 of 4 runs; 1 partial, 1 not captured" for a gap, "None seen" only over complete runs, "None seen in 7 complete runs; 2 not captured" over a mixed column (dashed glyph), "Not captured" when no run of the column was captured. The cell opens a popover (a bottom sheet below `md`, which returns focus to the cell) with every event and the hits and coverage of each run in a scrolling region (the popover grows to 60% of the viewport) with a focus ring; "Open in Hits" is pinned below it and always reachable. When no tag was seen but some runs were partial or not captured, the empty state says the observation is incomplete and counts those runs. A fourth control, Events or Consent state, switches the cells to "Observed consent state before and after the choice": each cell lists the combinations the tag's hits carried as "Ads denied · Analytics denied: 7 hits" (Ads is `ad_storage`, Analytics is `analytics_storage`), split into "Before the choice" and "After the choice", "Mixed: 2 states" when there is more than one combination, "No hits" for an empty bucket and "Not applicable, no choice seen" after the choice when no run of the column had its choice seen (the before bucket is then titled "All hits (no choice seen)"). Meta and TikTok cells say "No consent signal on these hits" and give hit counts. Column headers add the outcomes ("3 runs: Choice: accepted", "No choice made", "Choice not seen (no banner found)") and the banner. The popover offers "Open n hits before the choice" and "after the choice". The controls are three labelled groups (View: viewport and columns; Pages or Scenario; Show: Events or Consent state). "How to read it" is a button with a `?` icon beside the heading that opens a popover explaining n/m and ×n, or the consent words, and says this is the state the hits carried, not the order of the consent commands (`consent.default-after-tag`). Rows are `py-2`/`py-3`. The table scrolls inside its container with the first column sticky; the audit tab bar scrolls sideways below `sm` instead of wrapping.

**Hits.** A timeline of decoded hits and `dataLayer` pushes, 200 per page. A search box (event, destination, ids, parameters) and "+ Vendor / Event / Destination / Scenario / Source / Timing / Run" chips (Source is "Network requests" or "dataLayer pushes"; a chip with more than two values reads "Run: 5 runs" with the list in a tooltip) (Destination is the exact destination ID, with several values; Timing is "Before the choice" or "After the choice", one at a time, and "before" holds every hit of a run with no consent action); below `md` they sit in a "Filters" sheet. Destination and Timing apply to hits only, like Vendor and Event, so the matrix links add `source=network`. A count line comes from the server ("11 of 342 hits · 40 of 120 pushes"), then one legend line for the columns. The table has Run ("#1 /clean/ · No interaction", full URL in a tooltip), Time, Vendor, Event, Status (the HTTP status or "Answered locally"), Consent ("Ads denied · Analytics denied", "No signal" for Meta and TikTok) and Destination; Key params appears from 2xl up. Vendor reads like the Tag matrix ("Google Analytics 4", `vendorName` in `lib/tag-matrix.ts`), in the table, the Vendor filter, and the detail. The table takes the full width until a row is selected; then the detail pane (26rem) opens beside it and Status, Consent, Destination and Key params make room for it (they are in the detail); below `md` the table shows Run, Vendor and Event only and the rest is in the sheet; the table scrolls inside its container with soft scroll edges; page labels drop the query, and the detail header adds "+ click IDs". A hit or evidence that cannot be loaded says why: "This hit is not available. Its stored capture is missing, so it cannot be shown again. Run a new audit to see it." for a 404 (local R2 is per checkout, so an audit made in another checkout has rows but no capture file), and "could not be loaded. The server did not answer; try again." with a Try again button for anything else (`LoadFailure` in `components/evidence.tsx`; the same for the finding detail, its explanation and evidence). Pushes show their event name and identical neighbours collapse ("6 pushes · 716–718 ms"). A neutral divider marks each run's consent action once. Under the table "200 of 687 items loaded" counts hits and dataLayer pushes together as the filters leave them (the count line above splits them); Load more fetches only the next cursor page, whose rows carry just the first four parameters, clipped, for the Key params column (the detail loads the rest). Rows are 32px high and the whole row is the click target, with the event name as the keyboard stop (32px); only ids, times, event names, destination IDs and raw values are monospace. Selecting a row loads only that hit, never the list. A row opens the detail (decoded consent as tokens, ids, parameters with copy, the request as Decoded or Raw) beside the list, or in a bottom sheet with previous and next below `lg`.

**Sign-in, sign-up, onboarding, invitations.** A narrow centred card (`AuthCard`) on a token gradient, under a 40px mark and one line of value copy ("See what your client's tags really do before consent."), with the page's own sentence and the form. Sign-in says what Zinko is and that password reset is not available yet; sign-up shows "8 or more characters". Onboarding says an organization is your consultancy or team and creates the first one ("Signed in as … · Sign out"). The invitation page names the organization and the role. Both forms use `noValidate` and the New audit pattern: `AuthField` ties an inline error and the hint to the input (`aria-invalid`, `aria-describedby`), the first invalid field takes focus, and a server refusal (wrong password, address already registered) shows once under the fields, with focus on the email field on sign-in and on the message itself on sign-up.

**Document titles and landmarks.** Every route sets its title with `head()` through `pageTitle` (`lib/page-title.ts`): "Clients · Zinko", "<Client> · Clients · Zinko", "Members · Settings · Zinko", and on an audit "<Tab> · Audit of <Site> · Zinko" (the site name from the audit loader through `auditTabTitle`; a `head` that reads `loaderData` must sit after `loader` in the route options or the route types turn circular). The sidebar `aside` is "Sidebar", the finding pane "Finding detail", the findings list a labelled region; Hits and the client page carry an `sr-only` h2 ("Hits", "Sites") and the hits and tag matrix tables an `sr-only` caption. While an audit runs an `sr-only` `role="status"` line says "n of m runs finished" at about every fifth of the runs, and the completion toast announces the end. Stat tiles read "Critical: 4 open".

**Settings.** Settings tabs share `tabLink` with the audit tab bar. Each page is `SettingsSection` blocks (title and description left, controls right from `lg`). ## Score honesty (batch I)

`components/score-figure.tsx` is the one place that shows a score: Overview (`hero`), Clients, client page, site history (`cell`) and the command palette (`inline`). It takes pure props (`score`, a `ScoreCoverage`, an optional band) so the report can reuse it. `scoreCoverage` in `lib/health-score.ts` sorts a score into two tiers. Tier 1, "Not fully checked" (muted number, partial glyph and words, a no-failures band reading "No failures in what was checked"): run coverage is incomplete, meaning some run has no check results or ended partial or failed (which covers an incomplete audit), or a client has a site with no audit. It states exact run counts ("1 of 2 runs checked", "2 runs did not finish", "6 sites not audited yet"). Tier 2: every run was evaluated but some checks could not be resolved. The number keeps full ink and a quiet line says "18 of 19 checks resolved"; a no-failures band reads "No failures in what was checked" with a dashed glyph, never a pass-sounding band. Tier 2 is deliberately quiet because it is near-constant: `hygiene.tag-errors` cannot tell when vendor requests are answered locally, so it is inconclusive on almost every audit, and a label on every audit would mean nothing. Full ink with the plain band and "All runs evaluated, every check resolved" only when every check resolved. The caveats disclosure still lists the unresolved rules. Banner uncertainty is a caveat on findings, not on coverage. The score formula and version are unchanged.

Counts have one definition each. "Could not check" is a rule whose finding has kind `inconclusive`: it could not be checked on any run it flagged and failed on none (a rule that also fails somewhere is a failing finding, not a could-not-check one). The Overview tile, the caveat (first 5 titles, then an "and n more" disclosure), the area strip, the Findings "Could not check (n)" group, the Clients table and the audits list all count that. Check results that could not run (`score.uncertainty.checks`) are a separate unit, named "checks". Findings coverage reads "36 of 40 runs evaluated; 4 did not finish": evaluated means finished with check results, and a partial or failed run is never counted as evaluated even when it has (inconclusive) check results. `ScoreFigure` shows "—" and "Not enough was captured to score" when half the runs or fewer were captured (evaluated and finished), in every size.

Layout: `PageContainer` (`max-w-5xl`, left-aligned) wraps Clients, client, site, New audit and Settings so they share the audit workspace's left edge; the audit workspace is full width. The Clients "Last audit" cell is two lines (status and time; inline score), and the mobile audit header hides the severity split, duration and "See why" to stay within two lines.

Overview top: one card with the large score and three tiles (Critical and Warning open, linking to Findings, and Could not check rules); then one "n caveats" disclosure (runs that did not finish with "See which runs", checks that could not run, undetected banner, mixed rules versions), open only when the audit is incomplete. The worst-finding prose is `max-w-prose` with its first sentence in foreground. Counts by area is one row per area with a segmented SVG bar (token fills, scaled to the busiest area) and the counts as linked text with glyphs.

## Report on paper

The Report tab's **Save as PDF** opens the browser's print dialog; the help line says to turn off headers and footers so the page address is not printed. In print only the report prints: the sidebar, header, tab bar, toolbar, edit controls, the Draft label and findings left out of the detail are hidden. The paper is always light, text is near-black, severity chips are an outline with their glyph (colour is never the only cue), and the cover, summary, scope, consent scenarios, findings, action plan and appendix each start a page.

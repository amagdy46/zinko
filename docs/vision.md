## What Zinko is

An open-source (AGPL-3.0) tracking auditor for consultants and agencies. It loads a client's pages in a real browser under each consent choice, records every tracking request, `dataLayer` push, cookie and consent signal, and turns that into findings with evidence and a white-label report.

The bet, from the research below: every competitor either needs an install on the client's site (Trackingplan, Elevar, Avo Inspector), reads configuration instead of behavior (Tracking Auditor, Measuremate, GAfix, Tag Diagnostics), covers only Google tags (Tag Assistant), or is a managed service priced for enterprises (ObservePoint, DataTrue at $16k+/year). Nobody open-source captures what actually fires, across vendors, per consent choice, from the outside.

## Principles

1. **Evidence, not opinions.** Every finding links to the decoded hit, the raw request, a screenshot and a cookie snapshot.
2. **Rules decide, the LLM explains.** Checks are deterministic functions over captured data. The LLM (bring your own key) writes explanations and fix steps, never pass or fail, and every check works without it.
3. **No install on the client's site.** Zinko audits from the outside, so it works before a sale and for one-off audits.
4. **Audits fail partially.** Each page × scenario is its own step; a failed step records a typed error and the report still renders.
5. **Cross-vendor.** GA4, Google Ads, Meta and TikTok first; the decoders are data plus small functions, so more vendors are cheap.
6. **Self-serve and open.** No credits, no seat pricing, the API on every tier. The paid cloud sells hosting, scheduling and alerts, not access to features.

## How a run flows

```
New audit form (apps/web)
  → startAudit: audit + runs (page × scenario × viewport) in one transaction
  → Audit workflow (Cloudflare Workflows, instance id = audit id): start, then per run
    admit-<n> (AdmissionGate Durable Object hands out a grant, FIFO per capture)
    → capture-<n> (confirm token, capture, store, release) → persist-<n> (or fail-<n>)
    → next run joins the tail; Lost/Retry uses admit-<n>.<turn> and capture-<n>.<turn>
    → finish after every run
      → Browser service → apps/browser container (Scrapling AsyncStealthySession; Playwright fallback)
          init script: dataLayer shim + autoconsent → load page → requests (with POST bodies),
          dataLayer pushes, cookies, CMP state, screenshot
      → packages/decoders: request → Hit
      → store: capture.json and screenshot in R2 (Storage service), then hits and pushes
        derived from the stored capture into Postgres (Drizzle)
      → packages/rules, in persist-<n>: the run's capture and hits → check_result rows,
        written in the same transaction as the hits
      → AuditRoom Durable Object (AuditProgress service) pushes progress to open tabs
  → finish: check results → finding rows (deterministic; triage kept apart in finding_triage)
  → Llm service: explanation and fix steps per finding, cached
  → Findings, Tag matrix, Hit explorer, Report
```

Effect services live in `packages/core`, layers are wired in `apps/web/src/server/layers.ts`. Decoders and rules stay plain TypeScript so the CLI can reuse them without Cloudflare.

### What blocking does not guarantee

`blockVendorRequests` refuses any request whose method, path and query match a shape in `isCollectionRequest` (`@ovriq/zinko-decoders`, mirrored to `apps/browser/src/inject/collection.json` by `packages/decoders/scripts/engine-endpoints.mjs`, which `pnpm build` checks), on any host, first-party collectors included, before it leaves the browser. Known vendor host suffixes stay blocked as a second layer. A blocked request is recorded with `blocked: true` and answered locally. It is a best effort, not a privacy guarantee:

- A vendor Zinko has no decoder for: its custom endpoints are neither recognised nor, unless the host is listed, blocked.
- A recognised vendor sending a shape we do not list (a new GA4 or Meta path, a changed query) through a first-party path, such as a server-side GTM container on `/metrics/x`, or a CNAME collector on a path other than the listed ones.
- Plain HTTPS tunnels seen only by the proxy: it cannot read their paths, so path matching depends on the engine's own request interception.
- The SDK files themselves are still downloaded from the vendors, by exact file path only (`gtag/js`, `gtm.js`, `fbevents.js`, `signals/config/<id>`, TikTok `events.js` and `static/*.js`).
- WebSockets: one opened to a vendor host or a collection-shaped URL is refused before it connects and recorded (`resourceType: "websocket"`, `blocked: true`), but the messages of any other socket are not classified, so a payload sent over an established socket to an unrecognised URL is not seen. Playwright routes sockets with `context.routeWebSocket`; patchright's version never fires, so the Scrapling engine wraps `window.WebSocket` in every frame instead. Both engines also guard sockets in about:blank and `srcdoc` iframes, and the wrapper coerces the URL once and connects to the string it checked. **A WebSocket opened from a Web Worker (dedicated, shared or service) is not blocked or recorded on either engine.** Verified with a blob worker opening `ws://localhost/g/collect?v=2` and a probe server: the socket connected under both. `context.routeWebSocket` and the page wrapper do not run in workers; an attempt to inject the guard through CDP (`Target.setAutoAttach` with `waitForDebuggerOnStart` for `worker` targets, then `Runtime.evaluate`, then a `Debugger` breakpoint at the script start) put it in a realm the worker script did not use, and the breakpoint never fired, so it was dropped rather than shipped unreliable. Open: patterns for `Network.setBlockedURLs` in worker sessions (they would be wildcards, not the shared list).
- A page that sends data to a first-party endpoint with an unrecognised shape reaches the site's own server, which may forward it. Zinko cannot see that.

Audit a site you do not own only with this limit in mind; the run records what was answered locally so rules and the UI can say so.

## Open questions

- **Bot protection:** on the 2026-10-20 test pages Scrapling passed the checks that flag plain Playwright (`HeadlessChrome`, `navigator.webdriver`; BrowserScan "Normal" vs "Robot", CreepJS 33% vs 100% headless), and both fail the SwiftShader WebGL check. Still open: how protected sites treat Cloudflare Container (datacenter) traffic, and real Cloudflare challenges, since nowsecure.nl's forced-interactive Turnstile test key stopped both engines and `fetch()`'s solver alike. Also open: container cold start and cost for 10 pages × 3 scenarios.
- **Audit throughput:** captures run one at a time per audit. Task 5 measured 12.8 s per run locally, so 10 pages × 3 scenarios (30 runs) take about 6.4 minutes against the 5-minute target, before container cold start; the demo's complete audit ran at 10.1 s per run, which is about 5.1 minutes, so the target is missed or met by a hair depending on the pages and the network, and one 30 s navigation timeout (as in the demo's first audit) costs more than that margin. The form's estimate uses 7 s per unit and the running audit's time left follows its measured pace. Parallel captures within an audit (several container instances, or several pages per engine) move to a later milestone. Concurrent audits take turns on the engines through the `AdmissionGate` (see Capture admission above): locally one capture at a time on `BROWSER_URL`, on Cloudflare up to three captures at once on named containers (`maxInstances` 3). Each audit has at most one capture in flight, and joins the tail again for its next capture.
- **Admission control for captures (revised 2026-10-22, `docs/decisions/0003-capture-admission.md`):** a FIFO gate hands out one engine per capture, releases it after storage before persistence, and fences retries with a confirmed grant token. Short audits can finish before an earlier large audit; shared named slots remove the old per-audit container constraint. Still open: per-organization limits or weighting (the queue is global), production container behavior, and migration of workflows already executing the former definition (drain them before rollout).
- **Consent timing of hits (decided in M2 Task 5 review):** gtag sends what it held under Consent Mode within milliseconds of the click, before autoconsent reports completion (`ga4-batch` under accept: action at 10,060 ms, the batch at 10,074 ms, completion at 10,081 ms). So `after_consent_action` is `startedAt >= consent.actionAt`, and the CLI's "after" marker uses the same rule. It is false whenever there was no action (`none`, `gpc`, `not-found`) or the action was not seen to take effect (`not-applied`: the choice is unknown, so no hit is marked as following a verified choice), so M3 rules branch on `consent.outcome` first rather than reading `false` as "before consent". The CLI's marker still counts from `actionAt` under `not-applied`, to show what followed the attempt; it prints the outcome above the table.
- **Ads conversion redirect hop:** without `blockVendorRequests` a googleadservices conversion can redirect to `google.com/pagead/1p-conversion/…`, which the decoder reads as a second conversion with the same label, so `duplicates.purchase-sent-twice` would count it. Every audit blocks vendor requests today; revisit before allowing unblocked audits.
- **Banners autoconsent cannot operate:** the engine now reports choices it cannot verify (`not-applied`, with an observed-failure or unverified verdict) instead of trusting autoconsent, but does not make them work. Happy Socks' Cookiebot dialog rejects (autoconsent's `Cookiebot.withdraw()` path) but does not accept: autoconsent's Cookiebot opt-in clicks `#CybotCookiebotDialogBodyLevelButtonAccept` and `#CybotCookiebotDialogBodyButtonAccept`, and returns `true` whatever it clicked; most likely that dialog's button has another id (not checked: one capture per scenario on that site). Open: fix such CMPs upstream in autoconsent, keep our own rule overrides, or fall back to a CMP's JavaScript API (`Cookiebot.submitCustomConsent`), which skips the click a visitor makes and so would not catch a broken button.
- **`gcd` decoding:** sources disagree on the letter mapping, so any `gcd` rule stays heuristic until verified.
- **Proposed features above:** decided in M3. Three outcomes, Google's wording and click IDs through redirects are in v0.1 and working; the approved vendor list per client moved to a later milestone (it needs client settings). GPC is in M1 and working.
- **Region simulation:** emulate (headers, timezone, locale) or actually route through a region; emulation may not trigger server-side geo logic in CMPs.
- **Deploy:** the workflow is manual-only with a required `stage`, per-stage environments and a database-name guard (decision 0004, Part A). Open: the real deploy, container size and cold start, and the engine fallback, all behind owner gate Q13.

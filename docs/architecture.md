# Zinko architecture and stack

The stack follows the Ovriq house stack: **Effect 4 on Cloudflare**. See [decision 0001](decisions/0001-effect-and-cloudflare.md). The scaffold is generated by [efforge](https://github.com/amagdy46/efforge); `efforge.jsonc` at the repo root lists the choices (Postgres, Drizzle, better-auth with organizations, Alchemy, Effect AI BYOK, and the workflows, realtime, browser, storage and email add-ons). Add or change parts with `efforge add`, not by hand.

## Comparing two audits (M6)

A comparison is never stored: it is a pure function of two audits' derived rows, computed on every read (`apps/web/src/lib/compare.ts`, read by `server/compare-data.ts`). The unit is a cell: page × scenario × viewport × journey, built by one function (`cellKeyOf`) from the run and the audit's config, so the comparison, the regression history and the re-check targets cannot drift apart. A finding is judged only on the cells both audits ran and checked with the same consent outcome and banner detection, and only when the rules did not change between their versions (`RULE_CHANGES` in `packages/rules`); every cell that failed before stays in the picture until it is positively resolved, so a missing, failed or incompatible cell is never "fixed". The states are new, regressed (a cell-level search of up to ten earlier audits), unchanged (with narrowed, widened or moved), fixed, verdict changed and not comparable.

What a person decides is stored and nothing else: the baseline link (`audit.baseline_audit_id`), the triage and report edits copied once into a new audit with their origin, and re-checks. A re-check is an ordinary audit with `kind = 'narrow'` whose runs carry a role (target, banner-detection companion, extra); every reader of results filters to the targets, and the finding rows of a narrow audit are rebuilt from them. The report freezes the part a client sees (`ReportModel.changes`, projected through the author's exclusions); its publication stamp fingerprints what the comparison read so a re-check finishing during a publish forces a re-read.

| Core library | **Effect 4** (`effect@4.0.x`) | Typed errors fit "audits fail partially"; services and layers keep Cloudflare out of the core; one style across Ovriq |
| Cloudflare bindings | **effect-cf** (Effect-native Workers, Durable Objects, Workflows, Queues, R2) | Bindings as layers instead of a global `env` |
| Monorepo | pnpm workspaces + Turborepo | Already set up |
| Web | **TanStack Start** on Workers via `@cloudflare/vite-plugin`, + TanStack Router / Query / Table | Server functions call into one `ManagedRuntime` |
| UI kit | Tailwind v4 + shadcn/ui (Radix) + lucide icons | Owned components, accessible, fast to build |
| Validation | **Effect Schema** | Replaces Zod; shared by server functions, rule config and LLM output |
| Database | **Postgres (Neon) through Hyperdrive**, **Drizzle** (`drizzle-orm/effect-postgres`); `drizzle-kit` generates the migrations, `pnpm db:migrate` applies them | Postgres keeps a non-Cloudflare self-host path open; D1 would not |
| Auth | **better-auth** + organization plugin, on the same Postgres | Workspaces, invites, roles; runs on Workers |
| Orchestration | **Cloudflare Workflows**: one workflow instance per audit (instance id = audit id); per run an `admit-<n>` step (an engine from the admission gate), a `capture-<n>` step, then `persist-<n>` or `fail-<n>`; `start` before them, release in each capture finalizer before persistence, and `finish` after | Durable retries per step; a failed run does not stop the audit; replaces pg-boss |
| Live progress | **Durable Object per audit** (`AuditRoom`) with hibernating WebSockets, behind an authenticated Worker route (see Realtime below) | Replaces SSE-from-Postgres |
| Capture admission | **One Durable Object** (`AdmissionGate`, `docs/decisions/0003-capture-admission.md`): a FIFO line for the engines in `Browser.engines`; each capture joins the tail, confirms its grant token before every browser attempt, and releases after storage before persistence; waiters sleep in `waitForEvent` and are woken by an `engine-free` event | Capture turns follow FIFO order across audits; short audits can finish before a large one; replaces independent 429/503 backoffs |
| Browser | **Scrapling 0.5** (`AsyncStealthySession`, Python, on patchright) in a Cloudflare Container, behind the `Browser` service ([decision 0002](decisions/0002-capture-engine.md)) | Stealth browser launcher; `capture.py` drives the page with the Playwright API (routes, request listeners, cookies, screenshot) rather than Scrapling's `fetch()`. Every capability capture needs works, some through `additional_args`. Less visible to fingerprint checks than plain Playwright (spike RESULTS.md, 2026-10-20) |
| Browser (fallback) | Plain Playwright + Chromium in the same container (`apps/browser/src/engines/playwright.ts`) | Operational fallback, picked per request when Scrapling fails to launch or with `CAPTURE_ENGINE=playwright`, and the comparison baseline. Shares the shim, vendor list and autoconsent bridge; `engine` on the result says which ran |
| Browser (egress) | A per-capture HTTP proxy in the Node server; Chromium starts with `--proxy-server` | Playwright routes never see redirect hops, so the SSRF policy and `blockVendorRequests` are enforced where every connection passes |
| Browser (quick checks) | Browser Rendering (`@cloudflare/playwright`) | Cheap quick checks; optional, not built |
| Consent clicking | **@duckduckgo/autoconsent** (MPL-2.0), injected in the container | Deterministic accept/reject for common CMPs |
| Files | **R2**, through the `Storage` service | Screenshots and captures now; PDFs later |
| LLM | **`effect/ai`** (Effect 4) with the Anthropic, OpenAI and OpenRouter providers; Ollama through the OpenAI-compatible client | Bring your own key, encrypted per workspace; audits work without a key |
| PDF | The container prints the report route with `page.pdf()` | Reuses the browser |
| Email (invites) | Cloudflare Email Service | Same platform |
| Lint / format | **Vite+**: oxlint and oxfmt, plus the Effect language-service diagnostics | One `vp check` for format, lint and types |
| Infra as code | **Alchemy** (`alchemy@2`, "Infrastructure as Effects") in `infra/alchemy.run.ts`: `Cloudflare.Website.Vite` for TanStack Start, Workflows, Durable Objects, Containers, R2, Hyperdrive, plus the Neon project and branches | Infra in TypeScript and Effect, same as the app; no hand-written `wrangler.jsonc`; a Neon branch + Worker per PR preview |
| CI / deploy | GitHub Actions: check, typecheck, build, `alchemy deploy` (per-PR stage, destroyed on close) | |

## Packages

```
apps/
  web/          generated, now Zinko's app: TanStack Start on Workers (UI, server fns, auth, clients and sites, audits); hosts the `Audit` workflow, the `AuditRoom` and `AdmissionGate` Durable Objects and the `BrowserContainer`
  browser/      Zinko: the capture container image (Node server, egress proxy, Scrapling engine in scrapling/, Playwright fallback)
  cli/          Zinko: `decode` and `capture` (against the engine; `--rules` runs the same rules as the app), no Cloudflare
packages/
  core/         generated: Effect service interfaces (Database, Auth, Storage, Llm, Browser, ...)
  db/           generated: Drizzle schema, migrations, Effect SQL layer
  decoders/     Zinko: request -> Hit (GA4, Google Ads, Meta, TikTok; pure TS, no Effect)
  rules/        Zinko: `evaluateRun` (one run's capture and decoded hits -> one check result per rule, with evidence references) and `decodeHits`; pure TS, no Effect, shared by the workflow and the CLI
  capture-contract/  Zinko: Effect Schemas for POST /capture, shared by the web app and the CLI
  fixtures/     Zinko: fake shops, each with one known tracking bug, plus a server and an `inspect` script
infra/
  alchemy.run.ts  generated: every Cloudflare resource, per stage
planned: llm, plan
```

Zinko's own packages (`decoders`, `rules`, `capture-contract`, `cli`) are plain TypeScript and follow the workspace's TypeScript 7, catalog dependencies and `vp check` rules (including `no-console`; the CLI writes through `process.stdout`).

### Where Effect goes

- **Pure code stays plain:** decoders and rules are pure functions, and stay easy to test and reuse in the CLI.
- **Effect at the edges:** anything with I/O, retries, timeouts or failure modes (capture, DB, R2, LLM, workflow steps) is an Effect service in `packages/core`, with a Cloudflare layer in `apps/web` and a Node layer in `apps/cli`.
- **Error codes are tagged errors:** `BotBlocked`, `Timeout`, `CmpNotFound`, … map 1:1 to the partial-failure codes shown in the UI.

## Data model (v0.1)

The source of truth is `packages/db/src/audit-schema.ts` (migrations in `packages/db/drizzle/`). Every table carries `org_id`, and everything below an audit is reached through its owning audit, checked against the organization; an id from another organization behaves like a missing one (404).

```
organization ─< member >─ user              (better-auth)
organization ─< client ─< site ─< audit ─< run (page × scenario × viewport, `ordinal`)
                                           ├─< hit             (decoded, jsonb params)
                                           ├─< datalayer_push
                                           ├─< check_result    (one per rule; evidence references)
                                           └─ R2 keys: screenshot_key, capture_key
audit ─< finding            (derived from check_result by `finish`)
audit ─< finding_triage     (people's calls; no foreign key to finding)
organization ─ llm_credential (provider, encrypted key, model)
later: report_share and branding (M5)
```

| Table | Key columns |
|---|---|
| `client` | `id`, `org_id`, `name`, `archived_at` |
| `site` | `client_id` (restrict), `name`, `origin`, `host` (canonical; the allow-list), `archived_at` |
| `audit` | `site_id` (restrict), `created_by`, `config` (jsonb `AuditConfig`), `status` (`queued`, `running`, `complete`, `partial`, `failed`), `error` (launch failures), `workflow_id`, `started_at`, `finished_at` |
| `run` | `audit_id` (cascade), `ordinal` (unique with `audit_id`), `page_url`, `scenario`, `viewport`, `status` (`pending`, `running`, `complete`, `partial`, `failed`), `failure` (`EngineFailure`, `EngineBusy`, `PersistFailure`; null when the engine refused the request), `engine`, `decoder_version`, `consent`, `documents`, `cookies`, `errors` (all jsonb), `complete`, `truncated`, `screenshot_key`, `capture_key`, `hit_count`, `started_at`, `finished_at` |
| `hit` | primary key `(run_id, request_id, batch_index)`, no `id`; `document_id`, `at` (ms since capture start), `vendor`, `destination_id`, `event`, `params`, `ids`, `consent`, `host`, `url`, `blocked`, `status`, `after_consent_action` |
| `datalayer_push` | primary key `(run_id, seq)`, no `id`; `document_id`, `at`, `value` |
| `check_result` | primary key `(run_id, rule_id)` (cascade from the run); `rules_version`, `status` (`pass`, `fail`, `inconclusive`, `not_applicable`), `message`, `evidence` (jsonb `EvidenceRef[]`), and the rule's `area`, `severity`, `title`, `why`, `fix` as they read when the run was judged |
| `finding` | primary key `(audit_id, rule_id)` (cascade from the audit); `kind` (`fail`, or `inconclusive` when no run failed and one could not be checked), `rules_versions`, the stored text, `failing_runs`, `inconclusive_runs`, `run_ids` |
| `finding_triage` | primary key `(audit_id, rule_id)`, no foreign key to `finding`; `status` (`open`, `accepted_risk`, `fixed`), `updated_by`, `updated_at` |

- **Evidence is archived, never deleted by accident.** Foreign keys from audits upward are `on delete restrict`; a client or site with audits can only be archived (`archived_at`). Runs, hits and pushes cascade from their audit. Purging evidence (rows and R2 objects) is a later, explicit feature.
- **Natural keys make a rerun reproduce its rows.** `persist-<n>` deletes the run's hits and pushes and reinserts them from the stored `capture.json` in one transaction, with `created_at` set to the run's `finished_at`, so a retry gives identical rows, keys included. Check results and findings are derived the same way: evidence references name a hit by `(request_id, batch_index)`, not by a foreign key, so deleting and reinserting a run's hits never breaks a stored result.
- **The capture is written once.** `capture-<n>` reuses a `capture_key` already on the run, then an object already at `audits/<audit>/runs/<run>/capture.json` (found with `Storage.head`), and only then captures and writes. Workflow step results are capped at 1 MiB, so steps return keys, never captures.
- **Rules run inside `persist-<n>`.** The step decodes the stored capture with `decodeHits` (the CLI uses the same function), calls `evaluateRun`, and writes the run's `check_result` rows in the transaction that rewrites its hits, with `created_at` from the run's `finished_at`; `fail-<n>` deletes them, so a run that never persisted has none and the screen shows it as not evaluated. A run that is not `complete` (except one whose only errors are `CmpNotFound` or `ConsentNotApplied`) is `inconclusive` for every rule.
- **Findings are recomputed in `finish`,** in the transaction that settles the audit's status: one per rule that failed on a run, or failed on none and was inconclusive on one, with the text taken from the stored check results, not the live registry, so an old audit keeps its wording. `finding_triage` is never touched, so recomputing keeps people's calls. `getEvidence` resolves an `EvidenceRef` against the stored capture and the run's rows, through the audit, so the Findings screen can show the request, cookie or push that proves a finding.
- **`after_consent_action`** is `startedAt >= consent.actionAt`, false whenever there was no action (`none`, `gpc`, no banner) or it did not take effect (`not-applied`); rules branch on the run's `consent.outcome` first.

## Realtime

Live audit progress goes through `AuditRoom`, one Durable Object per audit named by the audit id (`apps/web/src/realtime/AuditRoom.ts`, bound as `AUDIT_ROOM`). It hibernates its sockets, accepts at most 50 of them and ignores whatever a client sends: browsers only listen, and the only way a message enters is the server-only `AuditProgress.publish(auditId, event)` (`@repo/core`), which the workflow calls and which never fails or stalls a step.

The room is reached through `/ws/audits/<auditId>` (`apps/web/src/server/audit-room-route.ts`, a `workerRoutes` entry), which refuses an upgrade before it touches the Durable Object, in this order: a malformed id (404); an `Origin` that is not the app's own, which closes the cross-site WebSocket hijack (403); no session (401); then `activeMembership(session)` (`server/org-access.ts`), which reads the `member` table, so a removed member whose session still names the organization is refused, and finally the audit looked up in that organization (404, the same answer as a missing audit). The room is named by the id the database returns, so URL letter case cannot select another room.

Events (`AuditEvent`, a `Schema`) carry a run's or the audit's new status; the page (`useAuditRoom`) validates them, reconnects with backoff, and refetches the audit on every event, when the socket opens and every 4 minutes (screenshot URLs expire after 5), so a missed event costs nothing. The scaffold's public `Room`, its `Realtime` service, `useRoom` hook and `/ws/rooms/*` route were removed.

## Key design rules

1. **Findings are deterministic.** Each rule is a pure function in `packages/rules`, checked against the fixture sites with `zinko capture --rules`. The LLM explains findings and suggests fixes but never decides pass or fail, and its output is cached per finding.
2. **Every finding cites evidence:** hit IDs, the request URL, a screenshot, and a cookie snapshot.
3. **Vendor matchers are data plus small decoders,** so endpoint changes are one-line fixes.
4. **Crawled pages are untrusted.** Their content goes to the LLM only as quoted evidence. The agent gets no credentials, and navigation is restricted to an allow-list of the site's domains.
5. **Read-only by default** toward GTM, GA4 and Meta when connectors arrive in v0.2.
6. **Audits fail partially, not completely.** Each run is its own `capture-<n>` and `persist-<n>` step pair; a run that is refused or runs out of retries is recorded with its error code (`fail-<n>`), the audit still finishes (`partial`, or `failed` when no run has a capture) and the report still renders.
7. **No Cloudflare in the core.** `packages/*` never import Workers types; only `apps/web` does. That keeps the CLI and a future Node self-host target possible.

## Self-hosting

- **v0.1:** deploy to your own Cloudflare account with `alchemy deploy` (Neon, or any Postgres URL for Hyperdrive). Free-tier friendly except Containers, which need Workers Paid.
- **Later:** a Node target (`@effect/platform-node` layers + Docker Compose) using the same packages, if self-hosters ask for it.

## Testing

No unit or integration tests in the current phase: we verify by running the real thing (the CLI, the engine, a capture against a fixture site). See "Current phase" in [AGENTS.md](../AGENTS.md).

## Open questions

- **Bot protection:** the 2026-10-20 comparison on 5 test pages (spike RESULTS.md) found Scrapling passes the fingerprint checks that flag plain Playwright (`HeadlessChrome`, `navigator.webdriver`), and both fail the SwiftShader WebGL check. Still open: real Cloudflare challenges (nowsecure.nl now serves a forced-interactive Turnstile test key that nothing passes, the `fetch()` solver included), BotD (its demo URL now 404s), and how protected sites treat traffic from Cloudflare Containers, since that run used a residential IP.
- Container cold start and cost for 10 pages × 3 scenarios; whether captures can run in parallel within an audit (several container instances, or several pages per engine) to meet the 5-minute target, since one capture at a time takes about 5 to 6.4 minutes for 30 runs. The engine runs one capture at a time per container and launches a browser per scenario. The containers are `maxInstances` (3) named engines, `engine-0` to `engine-2`, handed to audits in turn by the `AdmissionGate` (`docs/decisions/0003-capture-admission.md`).

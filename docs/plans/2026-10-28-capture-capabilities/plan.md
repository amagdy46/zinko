# Capture Capabilities Plan

**Goal:** The capture engine can do the three things the next research-driven rules need, and four rules use them. After a consent choice a journey run can reload the page and say, per document, whether the banner came back and what Google consent state the page settled in. A run can follow a real link to another host the site's owner declared, and say whether the visitor kept their consent and their analytics identity. Every script and tag request records who asked for it, so a finding can say "loaded by Google Tag Manager" or "in the page's own code" and the M5 report can name who fixes it. Rules: `consent.not-persisted-across-navigation`, `duplicates.purchase-on-reload`, `consent.lost-across-subdomain`, `clickid.crossdomain-linker-missing`. Demo: `zinko capture` against the new fixtures prints each fixture README's expected rule x scenario result set, and an audit's finding detail shows "Loaded by".
**Approach:** Every new contract field is `optionalKey`, so stored captures decode unchanged, and a rule that needs a field a capture lacks says "could not check", never "pass". One foundation does most of the work: for every document loaded after the consent action the capture records how it was reached (`navigation`) and whether the banner was shown (`banner`), observed in a bounded polling window rather than a single probe. The reload is a journey step, not a run kind, so it adds no runs. Cross-host is a `follow` step (click the real link: gtag decorates links at click time) plus a per-site list of hosts the owner declares, snapshotted into the audit's config; it adds at most three runs. Initiators come from CDP `Network.requestWillBeSent` on the main-frame session of both engines, shipped as their own checkpoint with byte limits, and are classified on read by a pure function in `@repo/rules` that attributes a cited request, not a vendor. No new dependency, no new table; additive columns only.

Design sources: `docs/roadmap.md` ("Rules from research", items 6 to 9), `docs/research/2026-10-28-pain-points.md` (rule ideas table), `docs/vision.md` (capture engine, "Site allow-list", "Journeys", "Consent scenarios", "Banner detection uncertainty", "Journey runs"), `docs/decisions/0003-capture-admission.md`, `AGENTS.md` (Rules, Capture admission, Storage, Database), `docs/plans/2026-10-27-m4-matrix-overview-llm/plan.md` (format), the M5 report plan (referenced by name only; it lives on branch `m5/report`), `review-r1.md` and `review-r2.md` in this folder, and the code as of `main` at the time of writing: `apps/browser/src/{capture,contract,server,egress-proxy,url-policy}.ts`, `apps/browser/src/engines/{playwright,cdp-frames}.ts`, `apps/browser/scrapling/capture.py`, `apps/browser/src/inject/datalayer-shim.js`, `packages/capture-contract/src/index.ts`, `apps/web/src/workflows/Audit.ts`, `packages/core/src/audit.ts`, `packages/db/src/audit-schema.ts`, `packages/rules/src/**`, `packages/llm/src/known-cmps.ts`, `packages/decoders/src/providers/ga4.ts`, `apps/cli/src/index.ts`, `packages/fixtures/**`.

## Decisions on the open questions

Settled by the orchestrator after review round 1; the plan below is written to them.

1. **Extra reload runs: deferred.** The reload is a step in journey runs only. A single-page reload run is a later plan.
2. **Same site: no new dependency, and nothing inferred.** Two hosts are related only when provable: the identical host, or a host the user listed in `site.measured_hosts` (an explicit declaration). Everything else is `unknown`, and a rule that depends on it answers could-not-check with the reason. Cookie-domain reachability is a separate, explicit check on a named cookie. A CMP's consent storage is identified only from an allow-list of known CMP cookie names (keyed by the CMP names in `packages/llm/src/known-cmps.ts`), never as "any new non-analytics cookie".
3. **Measured hosts: typed in first.** No suggestion or discovery in this plan.
4. **Severity: keep `warning`** for `consent.not-persisted-across-navigation`, for accept and reject alike.
5. **`*.localhost`:** resolved to loopback in the egress proxy only when private networks are allowed, and verified refused when they are not.
6. **Reload target: the last visited journey page,** shown in the audit form (not "the last key page": the workflow visits at most five).
7. **Real-site checks only on sites the owner authorizes:** for now the two M3 sites, Happy Socks and Allbirds. Attribution is described as "unverified on real GTM" until that check has been done.
8. **Run maximum: accept 171** (168 plus at most three cross-host runs).
9. **Attribution in the LLM digest: deferred.**
10. **CLI keeps today's open scope by default** (no `allowedHosts`), with an explicit `--allow-host` flag to opt in to the guard.
11. **Timing measured on a deployed build before the defaults ship.** Reload is on by default in the form only after that.

12. **Round 2 (orchestrator).** Network navigation scope and rule eligibility are separate (verdicts require the exact declared arrival host). Cross-frame attribution is refused and frame identity is kept. The verdict principle (see Global constraints) applies to every new rule. Task 7's initial allow-list is bounded as in "Initial CMP storage allow-list".

**Versions.** `main` is at `RULES_VERSION` "5" and the pending branch `rules/mode-classified-fix` takes "6". The rules here are numbered from "7" and the numbers are assigned at merge time: whoever merges next takes the next free value; the rule is that it rises whenever the rule set or a verdict changes. `DECODER_VERSION` stays "4" (GA4 `cid` is already decoded as `ids.clientId`; no decoder output changes).

## Global constraints

- **No unit or integration tests** (`AGENTS.md`, current phase). Each task is verified by running the real thing and reporting the command and what was seen: `zinko capture <fixture-url> --scenario all --rules --block-vendors` (with `--mobile`, `--goto`, `--reload`, `--follow`, `--allow-host` as the task says), the fixtures server (`pnpm --filter @repo/fixtures serve`), `node packages/fixtures/inspect.mjs`, `psql`, and the dev server in a browser at 1440x900 and 390x844 in both themes for any UI change.
- `pnpm check && pnpm typecheck && pnpm build` exit 0 with zero warnings after every task (real exit codes).
- **Fixture first** (`AGENTS.md`, Rules): the fixture site and its expected result set (rule x scenario x status) go into `packages/fixtures/README.md` before the rule exists, and `clean` stays at its baseline. The expected sets in this plan are the starting point, the README is the contract.
- **Both engines, same change.** Every engine change lands in `apps/browser/src/engines/playwright.ts` and `apps/browser/scrapling/capture.py` in the same task, and in `apps/browser/src/contract.ts` and `packages/capture-contract/src/index.ts`. `contract.ts` goes first: Node decodes checkpoints with it and drops an unknown field silently.
- **Backward compatible contract; old captures are unsupported, not absent.** Every new field is optional. A capture from before this plan has `navigation` undefined on every document. Rules distinguish that ("this capture predates reload and follow metadata": could not check) from an observed absence (every document has `navigation` and none is a `reload` or `follow`: not applicable). The test is `documents[0].navigation === undefined`. Both CLI consumers of "is this a journey" (`apps/cli/src/index.ts`, the `journey:` field in the explain-digest path and in the rules path) change from "has a `goto`" to "has a `goto`, `reload` or `follow`" (a click alone still does not count, as today).
- **Deploy order.** The browser app first (it accepts old and new requests), then the web app. A new step sent to an old engine is a 400 `InvalidRequest` and the run records a refusal.
- **Rules decide, rules are pure.** `evaluate(input)` stays a pure function of one run. Every `fail` cites evidence `getEvidence` resolves. Messages never print a value that may be personal data (the `_gl` value, a client id, an order id: they are named by position, never printed).
- **A rule that cannot tell says so.** Banner `unknown`, a Google consent signal missing on either side, a missing GA4 hit, an engine that did not record initiators: `inconclusive` with the reason.
- **Verdict principle (applies to every new rule, stated once).** (1) Any *established* failure wins: if one required observation shows the problem, the verdict is `fail` whatever else is unknown. (2) Otherwise, if any required signal, destination, document or purchase is unresolved (unknown, absent, ambiguous, ineligible), the verdict is Could not check (`inconclusive`) with the reason. (3) `pass` needs complete applicable coverage: every required item resolved and showing no problem. "Required" is defined per rule below; an item that does not apply to the run (for example a Google signal on a site with no Consent Mode at all) is not required, and the message says which items were considered.
- **Derived rows** keep `AGENTS.md`'s rule. Attribution is computed on read from the stored capture; it is not stored.
- **SSRF stays where it is.** Measured hosts widen the allow-list (scope), not the network policy: the egress proxy resolves every name and refuses private addresses, redirects included. Nothing relaxes `checkUrl`, `resolveHost` or `isPrivateHost`; the only new network rule is the gated `*.localhost` mapping (Task 6).
- **Docs move with the feature.** Each task ends by updating `docs/vision.md`; Task 11 sweeps. Vocabulary from `docs/ui.md`: Could not check (never "inconclusive" in the UI), Not evaluated (never clean).

## Scope and non-goals

In scope: the three capabilities, the four rules, the fixtures, one site setting (declared measured hosts), two audit options (reload the last visited page; follow declared hosts), the CLI flags, and the "Loaded by" annotation in the finding detail.

Not in scope: banner symmetry, regional defaults and more vendors (roadmap item 9); following links to hosts nobody declared; any verdict from initiators; initiators for out-of-process iframes and workers; a reload outside a journey run; form input and logged-in journeys; attribution in the LLM digest; Meta and TikTok order-id comparison in `purchase-on-reload` (the decoders carry no order id for them).

## Order and why

1. **Reload and per-document banner state (Tasks 1 to 4).** Smallest change, and it builds what the cross-host rules also need. Task 1 is the contract and both engines; Task 2 wires the workflow, form and CLI so Task 3 can be verified through a real audit; Tasks 3 and 4 are the rules.
2. **Cross-host follow (Tasks 5 to 8).** Settings and schema first (Task 5), then the step and run integration (Task 6), then the two rules (Tasks 7 and 8).
3. **Initiators (Tasks 9 and 10).** Independent of 1 and 2 and changes no verdict, so it can run in parallel from Task 2 on. If M5 starts first, pull it forward.
4. **Gates.** Two spikes decide scope and are explicit gates: the watch-only banner observation (Task 1) and the Scrapling initiator feasibility (Task 9). A gate that fails changes the task's scope as stated in the task; it does not block unrelated tasks.

Rule priority from the research: the two consent and click-ID rules are P1, `duplicates.purchase-on-reload` is P2 and the first to drop.

## Capability 1: a reload after the consent action

**Where it sits.** A reload is the last journey step: the journey run is the start URL, the consent action and its verification, up to five key pages as `goto` steps, then (with `AuditConfig.reload`) `{ action: "reload" }` on the page the journey ended on. Last, so click-ID rules still see the key pages as "the next pages", and so a run cut short by the deadline loses the reload first (its rules then say "the run ended before the reload"). The target is the last visited journey page, which is `pages[min(5, pages.length - 1)]` (the start URL when there are no key pages, at most the fifth key page: the workflow takes `pages.slice(1, 1 + JOURNEY_STEPS)`). The audit form prints that URL beside the option ("Reloads <url>, the last page the journey visits"; with more than five key pages it also says the rest are not visited). Evidence names the reloaded URL.

**What the engine records.** `page.reload({ waitUntil: "load" })` is a main-frame navigation, so `onRequest` opens a new document with the same URL. The step is `runStep`'s current sequence for a navigation: `flushBeacons`, the `document-end` snapshot, `checkpoint`, the navigation, `observeWindow`. New: `navigation` on every document (`start` where the first is created, `goto`/`reload`/`follow` by the step, `click` when a click changed `currentDocument`).

**Banner observation (gate).** The shim's `bannerShown(name)` returns `null` while `document.readyState !== "complete"` and when the CMP is not yet detected (`datalayer-shim.js`), and the Python engine checks frames one after the other (`capture.py` `banner_now`). A single probe at navigation commit would therefore be `unknown` on almost every page. Replace it with one bounded, document-specific window, `observeBanner(documentId)`:

- Starts when the document commits and runs alongside `observeWindow`; ends at `max(BANNER_MIN_MS, end of observeWindow)` but never past `WINDOW_CAP_MS` (10 s), with `BANNER_MIN_MS` 4 s.
- Polls every 500 ms; each poll asks all non-detached frames in parallel (`Promise.allSettled` / `asyncio.gather`), each with its own 1.5 s timeout, so a poll takes at most 1.5 s on either engine (the bound no longer depends on the frame count).
- Result: `shown` the first time any poll sees `true` (sticky: a banner that appears late is still seen, one that appears after the window is a known limit); `hidden` when the window ends with at least one definite `false` from a frame with the CMP detected and no `true`; `unknown` otherwise. The field is absent when the outcome is not `accepted`/`rejected` or the CMP is unknown.
- Mode separation: autoconsent stays injected after `settleConsent`, but in an explicit `watch` mode: the init reply sets `enableCosmeticRules: false`, and the only code that can dispatch `optIn`/`optOut` is `runConsent` (one call site, guarded by a counter `actionsSent` that the engine logs and a verification step reads). Watch mode answers `init` and `eval` messages and never dispatches an action.
- **Gate:** if the window cannot tell `hidden` from `unknown` on the delayed-CMP and cookie-restored fixtures below, the field ships as `shown`-or-`unknown` only (no `hidden`), the rule can fail on `shown` but never passes on banner evidence, and the plan says so in `docs/vision.md`.

**Per-document consent state (what the rules compare).** Both consent rules reconcile each signal chronologically; nothing is "the last hit wins".

- Signals: `ad_storage`, `analytics_storage`, `ad_user_data`, `ad_personalization`. For one signal in one document the *events* are (a) `consent` commands from that document's `dataLayer` pushes, at the push's `at` (`default` or `update`; an `update` changes only the signals it names, the others keep their previous value, so partial updates are exact), and (b) Google hits, at the hit's `startedAt`, each carrying a state for the signal from `gcs` (ad and analytics) and `gcd` (all four). If `gcs` and `gcd` disagree on a signal in one hit, that hit contributes `unknown` for it. Events are ordered by time (ties: the command first, then the hit).
- The state of a signal at time *t* is the latest event at or before *t*: `granted`, `denied` or `unknown` (a signal with no event, or a template-only default that never reached `dataLayer`, is `unknown`, never `denied`).
- The *reference* is the state of each signal at the end of the document the consent action ran in. Acceptance only means ad **or** analytics storage was granted (`playwright.ts` `choiceMatches`), so the *required signals* are the ones the reference shows as `granted`. No granted signal in the reference (a site with no Consent Mode, or only `unknown`): signals are not required and the verdict rests on the banner alone.
- A signal is *reverted* in a later document only when (i) its final relevant command in that document (the latest `default`/`update` naming it) is `denied`, or it has no command and (ii) a hit that carries a `denied` state for it happened at or after that command's time. A denying hit followed by a granting `update` is **not** a revert (the update is the final command); a granting hit after the final command contradicts a revert; a denying hit before the final command never counts. `unknown` never establishes anything.
- Banner recurrence is reported as observed behaviour ("the banner was shown again at the next page / after the reload"). No cookie is blamed unless Task 7's separate cookie check applies.

**Time and admission.** A journey of five key pages and a reload is seven documents (start, five, reload); `LIMITS.durationMs` 60 s + `perStepMs` 15 s x 6 steps = 150 s. The per-step figure is an average budget, not a guarantee: a navigation alone may take 30 s (`NAVIGATION_TIMEOUT_MS`) and the observation window 10 s (`playwright.ts`). The honest model is a total deadline, ordered so that cuts fall on the last steps: the reload is last; `remainingMs()` already shortens each navigation; the deadline is capped at `MAX_DURATION_MS = 200 s` regardless of step count, and the engine finalizes 6 s before it. The workflow's `capture` step has a 4-minute timeout and the admission lease is 5 minutes from `confirm`, so a 200 s capture plus startup, finalization (6 s) and storage (a few seconds) stays under both with a margin of about 30 s. Task 2 verifies it with a deliberately slow fixture (a `?delay=` response) at six and eight steps through the workflow, including the timeout path and the release of the grant. No extra runs, so the maximum and admission turns do not change. Engine time added at the maximum: eight journey runs x about 10 s typical.

**Storage size.** A reload adds one document (~250 bytes) and the reloaded page's requests and hits, once more, in at most eight runs per audit: well under 1 percent of the 226,918-hit stress audit.

**Both engines.** Both drive Playwright's API: `page.reload`, `frame.evaluate` and the polling window are the same calls; the Python engine mirrors them function by function. Neither lacks the capability.

**False-positive risks and answers.** `unknown` is never `shown`. A banner that is a persistent widget or re-prompt link is only `shown` when the CMP's own `detectPopup` says so. A CMP that re-asks after a period is still observed behaviour; the wording is neutral, not a legal verdict. A page-specific prompt from a different CMP is not seen (the check is for the detected CMP only); a second prompt from the same CMP on one page is rare and would be a true recurrence. A reload of a page reached by POST may resubmit or fail; a failed reload is a `JourneyStep` error, the run is partial, and `purchase-on-reload` says could-not-check (spike in Task 1). The reload revalidates from cache, so SDK scripts may not be requested again; collection requests are never cached and the rules read hits.

## Capability 2: cross-host journey steps

**Declaration and meaning.** `site.measured_hosts` (new `jsonb` column, default `[]`): other hosts the owner declares belong to the site: its tags measure them and a visitor should keep their consent and identity there. The settings text says exactly that ("Only add hosts where a visitor should not be asked for consent again and where your tags should recognise them. Zinko may open them and any of their subdomains."). Validation: canonical host, at least two labels, no IP literal, no port, at most 3, not private (`isPrivateHost`, unless `ALLOW_PRIVATE_SITES`), edited by owners and admins only (checked on the server), organization-scoped like every site column. This declaration is the only definition of "related" the rules use (decision 2).

**Snapshot.** `startAudit` copies the site's measured hosts into `AuditConfig.measuredHosts` when the audit is created. The workflow and run planning read the config, not the live site: `loadRun` today joins `site` for `host` (`Audit.ts`); `allowedHosts` becomes `[site.host, ...config.measuredHosts]` from the config, so editing the setting mid-audit changes nothing and a retried step sends the same list. `persist` passes `measuredHosts` into `RunInput`. The contract's `allowedHosts` limit (20) is far above 4.

**The step.** `{ action: "follow", host }`: on the current page find the first visible `a[href]` whose host is **exactly** `host`, scroll it into view, click it with a real mouse click and wait for `load`. A real click because the Google tag decorates links with `_gl` on click/mousedown/keydown; a `goto` never carries it. The step succeeds only if a new main-frame document committed (a JS-intercepted click that changes nothing, a same-page SPA transition, or a navigation that never commits is a `JourneyStep` error naming the host, not a pass). **Navigation scope and rule eligibility are separate.** Scope is what the guard allows: `allowedHosts` and their subdomains, so a redirect from the declared host to a subdomain is allowed to load. Eligibility is stricter: the two cross-host rules give a verdict only when the arrival document's host (the host of `documents[n].url`, after redirects) is exactly the declared host the run was planned for (`run.follow_host`, which is in `RunInput.measuredHosts`); an arrival on any other host, a subdomain included, is Could not check ("arrived at <host>, not at the declared <host>"). The arrival document records `navigation: "follow"`; its `url` and `redirects` are the request-time URLs (an intermediate redirect hop may carry `_gl` that the final URL lacks; a later `history.replaceState` is not visible), so the rules read `_gl` on any hop and never claim the final address bar. A popup stays refused. No matching link: `JourneyStep` error.

**Which runs.** With `AuditConfig.crossHost` on (form checkbox "Also follow links to the site's other hosts", shown only when the site has measured hosts) `startAudit` adds, after the journey runs, one run per measured host (at most 3): scenario `accept`, the first selected viewport, `run.journey = true`, `run.page_url` the start URL (click IDs on it when `clickIds` is on), `run.follow_host` the host. The workflow sends `journey: [{ action: "follow", host }]`. Accept only because both rules need the choice made and honoured on the first host; the linker is not viewport-dependent. Supported maximum becomes 171 runs; each is an ordinary admission turn.

**Time and storage.** A start page, the consent action and one step fits the 60 s + 15 s budget with room. Two documents, their hits.

**Both engines.** `follow` is `locator("a[href]")` filtering plus `click()` in both; the navigation guard (`Fetch` document pause and `framenavigated`) applies to clicks, so an unlisted host is refused the same way.

**Network policy (cleared by review, extended).** Main-frame `Fetch` interception guards every hop including redirects (`playwright.ts` `guardNavigations`, mirrored in `capture.py`), and the egress proxy resolves and connects to the address it checked (`egress-proxy.ts`). Task 6 extends the verification to both engines, HTTPS redirects, DNS rebinding and mixed answers (one public and one private address), credentials in the URL, deceptive host suffixes (`shop.com.evil.test`, `evilshop.com` against `shop.com`), and `*.localhost` with private access off.

## Capability 3: request initiators

**What a consultant needs.** For a cited request, who caused it: Google Tag Manager (which container), the page's own HTML or inline code, the site's own script, or another host's script.

**Engine.** An extra CDP session on the page (`context.newCDPSession(page)`, as the navigation guard already uses) with `Network.enable`, listening to `Network.requestWillBeSent`. **Scope: main-frame requests only.** Events are kept only when `event.frameId` is the main frame id (from `Page.getFrameTree`), and the Playwright side is joined only for requests whose `req.frame()` is the main frame. Requests from child frames and out-of-process iframes (which enter the context-wide `request` listener, `playwright.ts`) get no initiator: they are "not recorded", never guessed.

**Frame identity.** Every request keeps its frame: `CapturedRequest.frameId` (`f1` main, then `f2`... in order of first request) is assigned from the Playwright request's frame in both engines, which also covers out-of-process iframes (their requests enter the context-wide listener). Today every request carries the top-level `documentId` whatever frame made it (`playwright.ts` `onRequest`, `capture.py` `on_request`), so `documentId` alone cannot separate a main-frame loader from an iframe one; attribution uses `frameId`.

**Join, occurrence accounting and quarantine.** CDP records and Playwright requests are both restricted to the main frame (`event.frameId` against the main frame id; `req.frame()` main). Each side numbers its occurrences per key `method url`: the k-th record for a key pairs with the k-th request for it. Requests that exist without a counterpart are tombstones that keep the numbering aligned: a row the engine synthesizes from `Fetch.requestPaused` (intercepted redirect rows, `blockedRedirects`) takes an occurrence on the Playwright side, counted once even when `onRequest` later reuses it. A request answered by `route.fulfill`/`abort` is **not** a tombstone: Chromium still emits `Network.requestWillBeSent` for it before the route is exposed ([Playwright `crNetworkManager.ts`](https://github.com/microsoft/playwright/blob/main/packages/playwright-core/src/server/chromium/crNetworkManager.ts#L188)), so vendor SDKs and collection requests fulfilled under `--block-vendors` join normally. A tombstone is recorded only for a counterpart proven missing (reconciled against the CDP events actually received at the next flush), never assumed. Any loss makes a key unsafe: a record dropped by the pending cap, a count mismatch that persists past the next flush, a record for an occurrence already joined, or a redirect hop the engine cannot place. An unsafe key is **quarantined for the rest of the capture**: its unjoined requests get no initiator, and so do all later requests with that key; joins already emitted stay (they were made while the numbering was aligned). A join is **consumed** when emitted in an `initiators` checkpoint (removed from pending, never emitted twice); a record that arrives after its request was emitted is joined if the key is not quarantined and emitted on the next flush, which is why the checkpoint is separate from the request rows. Pending records are capped at 1,000 (oldest dropped, the key quarantined, counted in `initiatorsDropped`). If a stronger correlation becomes available (a Playwright request id that maps to the CDP `requestId`) it replaces this; until then the policy errs to no initiator.

**Reduction and limits.** Kept for `script` requests and requests to vendor hosts or recognised collection endpoints, vendor SDK scripts first. Each record: `type`, optional `url` (at most 200 characters, query removed), at most 6 frames (distinct script URLs from the stack and its async parents, query removed except the `id` of a `gtm.js`, each at most 200 characters): at most about 1.4 KB, typically 300 bytes. Aggregate limits per capture: 400 records and 256 KB of serialized initiators; beyond either, further requests get none and are counted in `initiatorsDropped` (attribution-specific; the capture's `truncated` stays untouched). Because initiators travel in their own `initiators` checkpoint, emitted once per request, a request row re-emitted when its status changes does not repeat its stack; the checkpoint counts against the 10 MB `resultBytes` budget like any data checkpoint.

**Scrapling (gate).** `capture.py` already calls `context.new_cdp_session(self.page)` and subscribes to CDP events (`guard_navigations`), so the handler is a mirror of the same size. Unverified: whether patchright lets a second session enable `Network` next to the `Fetch` session without disturbing its patches. Task 9 begins with a ten-line feasibility run. If it fails, that engine emits no initiators, every attribution reads "not recorded by this engine", and nothing else changes (no verdict depends on initiators).

**Classification** is the pure `loaderOf(input, ref)` in `packages/rules/src/attribution.ts`, run on read, never stored. It attributes a **cited request** (the hit's request or an SDK script request), not a vendor:

1. For a cited hit with `frameId` F in document D, the candidate loaders are the script requests in D **and in frame F** that are SDK files of the hit's vendor (`isSdkFile`). A cross-frame candidate is refused: a vendor SDK loaded in the main frame is never the loader of an iframe's hit (or the reverse), and a hit or script without a `frameId` (an old capture) is `unknown`. Initiators are recorded for the main frame only, so an iframe hit is `unknown` ("made in a frame that is not recorded") even when the main frame also loaded the same vendor. Exactly one distinct candidate: read its `initiator`. Zero: read the hit's own request `initiator` (an image pixel from a tag manager). More than one distinct loader (the same vendor loaded twice, as `meta-init-twice`): return `multiple` with each loader. Any ambiguity: `unknown`.
2. Classify the initiator: top frame is a `gtm.js` on any host (a server-side loader on the site's domain looks the same) -> Google Tag Manager, container from its `id`; `gtag/js` -> the Google tag; `parser` with the document as initiator -> the page's HTML; frames only the page's own document URL (inline script) -> the page's inline script; a script on the site host or a subdomain -> the site's own script (theme or plugin); a script on another host -> a third-party script named by host; no `initiator`, or no frames -> `unknown` with the reason (not recorded, engine, dropped).
3. Result: `{ kind: "gtm" | "gtag" | "page" | "site-script" | "third-party" | "multiple" | "unknown"; label; via; evidence: EvidenceRef[] }`, the evidence being the requests read.

It is an annotation; no rule consumes it. Until it has been checked against a real GTM container (Task 11, authorized sites only) the UI and docs describe GTM attribution as unverified on real containers: a custom HTML tag may inject a script whose async stack no longer includes the `gtm.js` frame, in which case the answer is `unknown`, never `gtm`. Fixture baseline correction: `clean` inserts gtag and the pixels dynamically from `tags.js` (`document.createElement("script")`), so their loader is `site-script`, not `page`; `page` is only expected for the new `loaders` fixture's literal tags.

## Rules

Ids, areas and severities; versions are assigned at merge time from "7" (see Decisions).

**`consent.not-persisted-across-navigation`** (consent, warning). `consentTimeline` first: `none` and `gpc` not applicable ("no choice was made"); `not-found` and `not-applied` could not check. Not a journey run: not applicable. Predates metadata (`documents[0].navigation` undefined): could not check. *Required items:* every document with `navigation` other than `start` that started after `actionAt` (none: not applicable), and for accept every required signal of the reference. *Fail* (established, wins over anything unknown): any such document has `banner: "shown"` (cites it: "the banner was shown again after the reload" / "at the next page"), or, for accept, a required signal is reverted in it by the chronological test above (cites the pushes and the denying hit). Reject checks banner recurrence only. *Pass* only when every required document has `banner: "hidden"` and every required signal is resolved `granted` in every required document. Anything else (a banner absent or `unknown` on one document, a required signal `unknown` in one) is could not check, naming the document and the signal.

**`duplicates.purchase-on-reload`** (duplicates, warning). Journey run whose last document has `navigation: "reload"` (else not applicable; predates -> could not check). Scope in v1 is **Google only**: GA4 `purchase` and the Ads `conversion` with a label and value, read through `purchases.ts`, whose `transactionId` reads `params.transaction_id`. Meta and TikTok are out of scope because their decoded events carry no order id (the fixtures' event ids are per-load nonces, not order ids); the rule says so in its "why" and does not report them as passes. Compare by `(vendor, destinationId, transactionId)`: the same triple in the reloaded document as in the document before it is a `fail` (cites both hits; the id is named by position, never printed). A purchase before the reload with no transaction id: could not check ("cannot tell a repeat from a new order"). None before: not applicable. Aggregation follows the verdict principle: any repeated triple fails; otherwise a purchase before the reload without an order id, or a post-reload purchase that cannot be matched, is could not check; pass only when every Google purchase before the reload has an order id and none of them appears again after it. It is not a verdict on server-side deduplication; the fix is to fire once per order.

**`consent.lost-across-subdomain`** (consent, warning). A cross-host run only: needs a document with `navigation: "follow"` and an `accepted` outcome (else not applicable, or could not check when the follow failed). Eligibility: the arrival host is exactly a declared host (see the separation above), else Could not check. Observed behaviour decides the verdict: fail when the arrival document's `banner` is `shown`, or when a required signal (granted in the reference) is reverted in it by the chronological test; pass only when the banner is `hidden` and every required signal is resolved `granted` there; could not check otherwise (verdict principle). The cause is a separate, explicit sentence, never part of the verdict: using the known-CMP cookie allow-list (`packages/rules/src/cmp-storage.ts`, keyed by `consent.cmp`: for example `cc_cookie`, `CookieConsent`, `OptanonConsent`, `euconsent-v2`, `didomi_token`, each verified against the CMP's documentation in Task 7), find that cookie in the `document-end` snapshot of the first document (the first document has `document-end`, not `end`) and apply `readableByScriptOn`-style reachability to the arrival URL (domain, path, `secure`, `httpOnly` handled as in `cookies.ts`): "its consent cookie `<name>` is limited to the first host" or "is readable on the arrival host but the banner was still shown" or, when the CMP is not in the allow-list or keeps consent in localStorage (not captured), no cause sentence ("the CMP's consent storage could not be identified").

**`clickid.crossdomain-linker-missing`** (clickids, warning). A cross-host run, accept, with a `follow` document whose arrival host is exactly the declared host (else not applicable / could not check as above; predates -> could not check). **Eligible hits.** Compare only GA4 hits whose `analytics_storage` is `granted` at the hit (its `gcs`/`gcd` state, `hit.consent.analyticsStorage`); an accepted choice can coexist with `analytics_storage: denied`, and cookieless measurement under denied storage does not carry a stable client id. A destination whose hits on either side are all denied or unknown is **ineligible**, not a pass. **Per destination** (GA4 measurement id): take the `ids.clientId` of the eligible hits on each side; more than one distinct client id on one side makes it ambiguous. `_gl` evidence: the parameter on the arrival document's URL or on any of its `redirects` hops. Outcomes: same client id -> the destination passes (identity carried, with or without `_gl`); different client id and no `_gl` -> *fail* ("the visitor was counted as a new user: no linker parameter on the link"); different client id **with** `_gl` -> *fail* with its own message ("the link carried a linker parameter but the destination did not adopt it"; typically `accept_incoming` or the domains list). **Aggregation (verdict principle):** any failing destination fails the run whatever the others are; otherwise every GA4 destination seen on the first document must be eligible and comparable and pass, and any ambiguous, ineligible or one-sided destination makes it could not check, naming it; a run with no GA4 hit at all is could not check. It never prints identifiers. The follow step's success condition (a committed document) plus the exact-host eligibility is the check that the click reached the intended host.

### Code review 2

1. **Reload guard races.** The check now runs last in the step, right before the reload, against the current committed document: refused (`JourneyStep`) when the document id is no longer the one the step began on ("the page navigated by itself"), a main-frame navigation is in flight, or the final method of the document is not `GET` (or unknown). New fixture pages `/post-form/timed?after=<ms>` and `/post-form/pagehide` (a GET page that submits a POST form by itself). Verified on both engines with `goto` then `reload`: on `pagehide` both engines refused ("navigated by itself"), one POST sent; on `timed` Playwright refused at `after=3300` (landed in the flush), Scrapling at `after=3000` (refused by method; at 3300 and later the timer fires during the reload and the reload replaces the page before any POST). A submission that lands after the check but before Chromium starts the reload remains possible in principle; it needs a timer within a few ms of the check.
2. **Deadline during a banner window (Scrapling).** The window tasks are owned by the capture: steps await them with `asyncio.shield`, `finish()` waits for open windows only when not finalizing (otherwise cancels them and records `unknown`), and `main` finishes through `finalize_safely`, which also catches `CancelledError` and still writes a bounded final checkpoint before `done`. Playwright's `finish()` does the same without waiting at the deadline. Verified: a three-step journey whose third page loads just before the 99 s finalize on Scrapling returned `Timeout` at 99 001 ms with the last document `banner: unknown`, an `end` snapshot, a screenshot and `done`. The same journey on Playwright finished with `Timeout` as well but its navigation had not committed (Playwright closes the browser on SIGTERM, an existing behaviour that also adds an `EngineFailure` for the screenshot), so it did not exercise the window.
3. **First step cut short.** The rule checks the cut-short errors (`JourneyStep`, `Timeout`, `Navigation`, `EngineFailure`) before it returns not applicable for "no later page": a capture with no later document and such an error is could not check ("the run ended before any later page"). Verified on a stored capture with its later documents removed (no error: not applicable; first-step click timeout: could not check). `evaluateRun` already answers could not check for every rule on any run with a non-consent error, which the CLI shows for a missing click selector.

**Known limit (reload guard).** The reload guard validates the committed document immediately before `reload`, but a form the page submits in the few milliseconds between that final check and Chromium starting the reload can still be re-sent. Closing it would need Chromium to refuse the reload itself; it needs a timer within milliseconds of the check, and the workflow only reloads a page it reached with a `goto`.

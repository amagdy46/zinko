# M6 Compare and Polish Plan

**Goal:** A consultant re-runs an audit with one click, opens a Compare tab and sees, finding by finding and tag by tag, what changed since the last audit of the same site: what was fixed (verified by the re-run, not just marked), what is new, what regressed after a fix, what can no longer be checked, and what cannot be compared at all and why. Accepted risks and notes carry over. A short "What changed" briefing leads the re-run's Overview and the client report. Then the product is releasable: empty and partial states are swept, the README and a self-host guide are true, a deploy to a real Cloudflare account has been tried, and a read-only public demo exists. Demo: "v0.1 release: a Show HN post and a 'we audited N sites' write-up" (`docs/roadmap.md`, M6).
**Approach:** A comparison is a **pure function of two audits' derived rows, computed on read**. Nothing about a comparison is stored except two human acts: the **baseline link** (`audit.baseline_audit_id`, set when an audit is created from a re-run or the New audit form, changeable by the consultant) and the **carried-over triage and report edits** (rows copied once, when the new audit is created, each marked with where it came from). The workflow does not change. The engine compares audits **cell by cell** (a cell is page × scenario × viewport × journey), judges a finding only on the cells that exist and have a verdict on both sides, and answers "not comparable" instead of guessing whenever the rule changed between the two rules versions (a hand-kept `RULE_CHANGES` registry), the banner was detected on one side only, or the scopes share no cell. States: new, regressed, unchanged, fixed, verdict changed, not comparable. A fix is "verified fixed" only when the re-run passes the check; the author's "Fixed" triage mark is a claim that the diff then confirms or contradicts. Tag-level changes (a tag disappeared, appeared, changed destination or event set) come from the same hits the Tag matrix reads. Real-site flakiness is not hidden by capturing everything twice; changes on volatile rules or rules that flip between audits carry a "low confidence" label and a **Re-run these pages** action, which is also the per-finding **Verify fix** (a small `narrow` audit of the pages and scenarios a finding failed on). The report gains a frozen `changes` section (`REPORT_MODEL_VERSION` 4, `UPGRADES` step, a validator for every new leaf). The polish half is a deploy spike first (it can fail, and the answer shapes the release), then docs, an empty-and-partial-states sweep, a demo instance seeded from real captures, and a release checklist that separates blockers from items that can wait.

## Global constraints

- **No unit or integration tests** (`AGENTS.md`, current phase). Each task is verified by running the real thing: the dev server in a browser at 1440x900 and 390x844 in both themes through the real theme menu, `psql`, `curl -i`, the CLI, and throwaway scripts in `$TMPDIR` (not committed). Report the command and what was seen. Screenshots go to `$TMPDIR/m6t<task>-*.png` (`TMPDIR=$HOME/.cache/tmp`). The comparison engine is the one place where a test would be natural, but the no-tests phase continues through v0.1 and is revisited afterwards (decision recorded under "Decisions on the open questions").
- `pnpm check && pnpm typecheck && pnpm build` exit 0 with zero warnings after every task (real exit codes).
- **Docs move with the feature.** Every task ends by updating the matching row of `docs/vision.md` ("Compare and polish") and, where it applies, `docs/ui.md` and `AGENTS.md`. Task 17 only sweeps and closes.
- **Comparisons are computed on read; the workflow is untouched.** `rg "baseline|carried_from|narrow" apps/web/src/workflows` stays empty. The only rows M6 adds are human acts (the baseline link, copied triage and edits, a narrow audit's `kind`), written by server functions inside the transaction that creates an audit. Nothing new is a derived row, so none gets a random id or `defaultNow()` in a way a retry could change.
- **Triage and report edits are still never rewritten by the workflow.** The one new writer is the audit-creation transaction (`createAudit`, carry-over in Task 4), which only inserts rows for an audit that has no rows yet. Afterwards `setTriage`, `saveReportEdit` and `saveFindingEdit` are the only writers, and they clear the inheritance marker. Amend both writer rules in `AGENTS.md` (the Database section line on triage, and the Report line on `report_edit` and `report_finding_edit`) in Task 4.
- **Org scoping and the 404 rule.** Every query filters by `org_id` and reaches runs, hits, check results and findings through `auditInOrg(orgId, auditId)`. A comparison takes two audit ids and checks **both**: either one from another organization, or the two on different sites, is a 404 (never a 403, never a message that says which). The baseline must be an earlier audit of the same site that was evaluated.
- **Stored wording, never the live registry.** Finding titles, severities, areas and owners in a comparison come from the `finding` and `check_result` rows (the side that has the row; the newest rules version's text wins when both do). `@repo/rules` is read for exactly two things that are not wording: `RULES_VERSION` and `RULE_CHANGES` (Task 5), plus the `VOLATILE_RULES` set (Task 9).
- **Vocabulary** (`docs/ui.md`): Could not check (never "inconclusive"); Not evaluated is never clean; no "healthy" or "clean". New words, added to `docs/ui.md` in Task 6: **New**, **Regressed**, **Fixed** (verified by a re-run; the author's mark stays "Marked fixed"), **Unchanged**, **Verdict changed**, **Not comparable**. Every state is a glyph and a word, never colour alone, and no new colour token: reuse `status-pass` for Fixed and neutral for the rest.
- **The report never leaks a page path or personal data through a comparison.** The report's `changes` section carries titles from stored static wording, counts, enums, dates and vendor labels. It names no page (pages are counted, because aliases ("Page 2") mean different pages in two audits). Destination IDs follow the existing rule (`destinationLabel`: ad-platform IDs only at the Detailed level). Every new leaf of `ReportModel` gets a validator in `LEAF_VALIDATORS`; an unregistered path fails the build as a defect.
- **No new dependency.** Existing shadcn components and shared blocks (`PageHeader`, `SectionHeading`, `EmptyState`, `StatusGlyph`, `lib/format.ts`). No diff library: the comparison is set arithmetic.
- **No inline `style`, no hard-coded colour, 32px targets, visible focus rings** (`AGENTS.md`). Any controlled `Dialog` or `Sheet` that opens from a menu item or a URL param restores focus (`ConfirmDialog` pattern).
- Never log the demo password or a token. `TMPDIR=$HOME/.cache/tmp`. No sudo, ever, in a worktree (Task 1 builds the container image in CI or with a rootless Docker, never `sudo pnpm`). Never push without asking. Migrations are generated, never edited. Never commit `.env`.

## Scope and non-goals

In scope: re-run with the same settings and the baseline link; triage and note carry-over; the comparison engine (finding states per cell, tag diff, comparability, regressed history, confidence); the Compare tab; narrow re-runs (Verify fix, Re-run these pages); the Overview briefing, Findings chips and site-history entry points; the report `changes` section and CSV columns; performance and security of all that; the empty and partial states sweep; README, self-host guide and contributor docs; a deploy spike (offline preparation now, the real deploy after owner gate Q13); a local demo seed, and a read-only public demo instance only if gate Q7 is answered yes; the v0.1 release checklist.

Not in scope: **single-run retry in place** (it gets its own later plan, decision 12); audit cancel; scheduled re-runs or alerts (v0.3); a stored `audit_comparison` table; re-judging an old audit's stored captures with today's rules ("re-evaluate", v0.2); comparing across sites or clients; comparing more than two audits at once (the trend is a sparkline already); a diff of raw requests, screenshots or cookies; region simulation (not a capture capability yet, so "region differs" cannot be detected: only the banner-detection and rules-version differences can); AI text about changes; consultant-typed page names; parallel captures inside one audit; a Slack or email "what changed" digest; billing.

## Decisions

| Question | Decision | Why |
|---|---|---|
| What is "the baseline" | `audit.baseline_audit_id`, nullable, **same site, earlier, evaluated, kind `full`**, `on delete set null`. Set at creation: by **Re-run** to the audit that was re-run, by the **New audit** form to the site's latest evaluated full audit (shown on the form with Change), and changeable later with **Make this the baseline**. Any earlier evaluated full audit of the same site can be compared by URL (`?against=`) without changing the link. `setBaseline` is refused while the audit is queued or running | A stored link gives the Overview, the report and the register one stable answer. A deleted baseline falls back to "no baseline", never to a guess. Freezing the link of an active audit closes the way round the in-progress guard (below) |
| Compare stored or computed | **Computed on read** from `finding`, `check_result` (without `message` and `evidence`), `run`, `finding_triage` and `hit`. The report freezes the result at publication | A stored comparison needs invalidation on every triage change, baseline change and confirmation, and would be a derived table with the determinism rules of `AGENTS.md`. The inputs are small (about 4,000 check rows per side). If a budget is missed: narrow the query or add an index, never a stored copy |
| Unit of comparison | **One canonical structural `CellKey`** and a **separate compatibility record**. `CellKey` = `{ page, scenario, viewport, itinerary, injected }`: `page` is the normalised **configured** URL of the capture (see "Injection" below: for an injected run it is the audit's configured start URL, otherwise the run's own URL, with its query kept); `itinerary` is `null` for a plain run and, for a journey run, the **actual capped itinerary** the workflow walks (`[pages[0], ...pages.slice(1, 1 + JOURNEY_STEPS)]`, `Audit.ts` `captureRun`/`capture`, `JOURNEY_STEPS = 5`, each normalised, in order; later config pages are not part of the key); `injected` is whether the audit's test click IDs were **actually applied to this run's URL**, recognised by `injectionOf(url)` (below), read from the stored run, not from the audit's `clickIds` setting. One function, `cellKeyOf(run, config)`, builds it, and **history, re-check targets (`narrow_cells`) and confirmations all use it and `sameCell`**. The compatibility record is per run and is never part of identity: `{ consentOutcome (class: applied `accepted`/`rejected`, or not applied `not-applied`/`not-found`/`none`), bannerDetection (`none` runs only), rulesVersion }`. A cell is *common* for a rule only when both runs exist, both have a check result for the rule and the **compatibility records agree** for the facts that rule's verdict depends on (consent outcome class for every accept/reject cell, banner detection for banner-dependent rules under `none`, the registry for the rules version); a disagreement is counted (`consentDiffersCells`, `bannerDiffersCells`) and the cell is neither common nor ever read as resolved | The scenario name does not say what happened; keeping identity structural and compatibility separate stops one set of rules (history, targets, confirmations) from drifting from another |
| States and precedence | See "State rules". Two central rules. (1) **Every cell that failed in the baseline stays in the picture** until it is positively resolved: a cell that is missing now, failed to capture, or is incompatible is never "fixed". (2) **Fixed requires that the rule fails on no cell at all in the current audit**, inside or outside the common set. Old failures resolved plus failures elsewhere (a moved failure, or a failure on a page the baseline did not run) is **Unchanged, spread Moved** (or Widened), because the current audit has the finding | A false "Fixed" next to a failing finding row is the worst thing this tab can print. `Audit.ts` aggregates a failing finding per rule across all runs, so the comparison must agree with it |
| Rules version difference | `RULES_VERSION` is global. `packages/rules/src/changes.ts` exports `RULE_CHANGES: Record<version, ruleIds[]>`: the rules whose verdict can differ for the same run in that version, **and the rules removed or reintroduced in it** (a rule only ever added, or only ever removed, needs no entry: it is not run on one side already). A rule is comparable unless some version `v` with `lo < v <= hi` lists it, where `lo` and `hi` are the lowest and highest versions that judged it in either audit; a rule that was absent in any version between the two (removed, then reintroduced) is therefore not comparable across the gap. Raising `RULES_VERSION` also means listing the changed rules (`AGENTS.md`, Task 5) | Reuses the existing discipline instead of refusing every cross-version comparison. Re-judging old captures with today's rules would be exact but is a v0.2 feature |
| Banner detection | `bannerDetection(orgId, auditId)` (M4) annotates `none` cells only (`consent-context.ts`). For `BANNER_DEPENDENT_RULES` under `none`, a cell whose detection class differs between the audits is removed from the common set, counted, and **kept on the "not re-checked" side of the resolution test** | The verdict of those rules depends on a banner existing; "fixed" because the banner was not detected this time would be a lie |
| Region | Not detectable (the capture contract records no vantage point). The Compare tab says so once, and `docs/vision.md` keeps region simulation open | Honest about what the data cannot say |
| Fixed by the author vs verified fixed | `finding_triage.status = fixed` is a **claim** and is not carried over. **Fixed** in a comparison is an **observation**. A finding marked fixed in the baseline that still fails reads "Marked fixed on <date>, still fails"; one marked fixed whose cells pass reads "Fixed, confirmed" | Separates what a person said from what the re-run saw |
| Carry-over | Copy once, at creation, inside `createAudit`'s transaction. Source = the baseline chosen at that moment. Copied: the source's `accepted_risk` rows (reason, `updated_by`, `updated_at` unchanged) and **all** its `report_finding_edit` rows (note, hidden, owner); `report_edit.detail` and `include_changes`; never the summary, `open` or `fixed` rows. Each copy records **`inherited_from_audit_id` (a plain uuid with no foreign key) and `inherited_from_at` (the origin audit's creation date)**; the origin is the source row's own origin if it has one, else the source. Because the marker has no foreign key and carries its date, deleting the origin audit never erases it, and **changing an audit's comparison baseline later changes nothing about its copies**. Editing a row on the new audit clears the marker. The Re-run dialog, the New audit form and the share dialog show a **preflight**: "From the audit of 14 Oct: 2 accepted risks, 3 notes, 1 finding left out" | The review's point: provenance must not depend on the mutable comparison link. Copy-on-creation keeps every reader (score "excluding accepted risks", Findings, report, register) unchanged |
| Capture twice to catch flakiness | **No.** It doubles the engine time and the admission queue for every audit. A change is labelled **Low confidence** when its rule is in `VOLATILE_RULES` (`consent.default-after-tag`, `consent.mode-classified`, `consent.google-without-denied-state`: the consent rules the roadmap saw change between runs of one page), when the rule's verdict on these cells flipped two or more times across the last five audits, or when it rests on a single run. The row offers **Re-check these pages** | The label and the optional re-check give the consultant the evidence without paying for it on every audit |
| Re-check (confirm and verify) | One server function, `recheck({ auditId, against?, ruleId })`, creates a `narrow` audit. Its **target cells come from the comparison** (the cells that failed before or fail now, or, with no `against`, the audit's own failing cells read from `check_result` rows with status `fail`, never from `finding.run_ids`, which also holds inconclusive runs). The audit stores `narrow_rule_id`, `narrow_cells` (the target `CellKey`s) and `narrow_companions` (banner-detection companion runs, executed but never counted as targets), so overlapping re-checks of different changes are told apart, and works for a finding that is **fixed** (it has no current `finding` row: the targets come from the baseline side). Its result counts only if every target cell has a complete run with a check result: "Re-checked on 2 of 3 cells" is **incomplete**, shown as such, and never reads as a pass | The first draft called `verifyFinding(currentAudit, ruleId)`, which cannot work for a fixed rule and treated inconclusive runs as failing ones |
| Narrow audits | Visible in the site history with a badge and no score; excluded from latest-audit selection, score trends, client aggregates and the baseline picker | Decision Q6 |
| Single-run retry in place | After v0.1, in its own plan | In-place retry rewrites a dated audit: capture and screenshot keys are deterministic, so old evidence is overwritten |
| Creating audits and the cap | Every creation path (`startAudit`, `rerunAudit`, `recheck`) goes through `createAudit`, which first takes a **transaction-scoped advisory lock keyed by the organization** (`pg_advisory_xact_lock(hashtextextended('audit-create:' || orgId, 0))`), then, still inside the lock: revalidates the baseline (exists, same org and site, older, evaluated, kind `full`), counts the organization's queued and running audits (at most 5), and applies the in-progress guard (refuse a re-run when an audit of the same site with the same baseline is queued or running; a `recheck` when a narrow audit with the same rule and overlapping cells is). The site-row lock is kept for the archived check only | The review: a site row lock cannot enforce an organization-wide cap, since two sites lock two rows. One lock per organization is cheap and is held only for the insert |
| "What changed" briefing | At most six deterministic lines from `changesBriefing(comparison)` (pure): regressions, new critical and warning findings, fixed, tags that disappeared, what could not be compared, then counts and score. Lines for uncertain changes are worded as uncertain ("may be a flaky result; not repeated on re-check") | Same discipline as `headlinesOf` |
| Score delta | An **unqualified delta** needs equivalent scope and context: both audits evaluated with full coverage, **no** cell present on one side only, no rules, banner or consent difference, same `SCORE_VERSION`. Otherwise both scores are shown without a delta and the reason. Both scores are read with **today's arithmetic** (`healthScore`, `SCORE_VERSION` 2); the Compare tab says so ("Both scores use score version 2") | The score is recomputed from findings on every read (`score-summary.ts`), so an old audit is already re-scored; the delta must not claim a like-for-like change when the scope differs |
| Tag-level diff | Per audit, the distinct (vendor, destination, event) of each cell; a cell is tag-comparable when both runs are `complete` | Elevar's missing-embed alert; a partial run missing a tag is "could not tell" |
| Report | `ReportModel.changes`, frozen in the snapshot, hash-included, switchable with `report_edit.include_changes` (default on). **Projected through the current audit's exclusions** (a finding left out of the detail is removed from items, lines and counts, and counted only in `omitted`), and every item carries its **confidence and confirmation** | Reviewer blockers 3 and 10 |
| Demo | See the owner gate Q7 and Tasks 16 to 18. If hosted: sign-up closed, one public credential, an **explicit mutation gate** and a **deny-by-default** auth policy, a demo runtime composition without a capture engine | Reviewer blocker 2 and finding 9 |
| v0.1 blockers | See "What blocks v0.1" | A release list with reasons |

## Data model

All additive and nullable or defaulted, so existing audits keep working. Each is added by the task that needs it with `pnpm --filter @repo/db db:generate`, then `pnpm db:migrate` (with `DATABASE_URL` exported).

```ts
// Task 3. audit-schema.ts
audit.baseline_audit_id: uuid references audit(id) on delete set null    // the comparison link; index (org_id, baseline_audit_id)
audit.kind: text not null default 'full'                                  // 'full' | 'narrow'
audit.narrow_rule_id: text                                                // set on a 'narrow' audit made by Re-check
audit.narrow_cells: jsonb                                                 // the target CellKeys of that Re-check
audit.narrow_companions: jsonb                                            // CellKeys of companion runs (accept/reject siblings) run only for banner detection
run.role: text not null default 'target'                                  // 'target' | 'companion' | 'extra' (cross-product runs that are not targets); set by createAudit

// Task 4. Inheritance provenance. No foreign key on purpose: it must survive the origin's deletion.
finding_triage.inherited_from_audit_id: uuid
finding_triage.inherited_from_at: timestamptz                             // the origin audit's created_at, so the date survives too
report_finding_edit.inherited_from_audit_id: uuid
report_finding_edit.inherited_from_at: timestamptz
report_edit.include_changes: boolean not null default true                // added here, BEFORE the copy that reads it
```

- **No `audit_comparison` table, no change log, no snapshot of states.** The comparison is a function; the report snapshot (`report_snapshot.model`) freezes the part a client sees.
- `AuditConfig` is unchanged: a narrow audit is an ordinary config.
- **Narrow audits** are excluded wherever "the latest audit", a score trend or an aggregate is chosen: `client-summary.ts` (the `counts`, the `lasts` select, the sparkline rank query), `clients.ts` (`searchTargets` recent audits, `getSite`'s `lastConfig` and the default baseline), `listClients`. ### Injection (`injectionOf`, `configuredPageOf`, pure, `lib/compare.ts`)

`withoutTestClickIds` (`lib/page-match.ts`) deletes every parameter **named** `gclid`, `fbclid`, `ttclid`, `utm_*` whatever its value, and configured URLs keep their own campaign parameters (`audits.ts` normalises but does not strip them), so a name-based test would read a real campaign URL as injected and collapse distinct campaign URLs. The comparison therefore never uses it for identity. `captureUrls` injects by `searchParams.set` of all six `TEST_CLICK_IDS` (`packages/core/src/audit.ts`) on page index 0 only when `clickIds` is on, which makes the injection recognisable by **values**:

- `injectionOf(url)` is true only when **all six** names are present with exactly the `TEST_CLICK_IDS` values (`ZINKO-TEST-GCLID`, …, `utm_campaign=zinko-audit`). A URL with a real `gclid=ABC123` or `utm_source=newsletter` is not injected.
- `configuredPageOf(run, config)`: for an injected run, the injection **overwrote** any same-named parameters the configured URL had, so the run's URL cannot give them back; the page is `config.pages[0]` normalised (the injected run is always the start page). For a non-injected run it is the run's own URL, normalised, query kept. Two different campaign URLs are therefore two pages, and the start page with and without injection has the same `page` and a different `injected`.
- **Older runs** need no migration or stored marker: injection has been a fixed set of six name/value pairs since M2, so recognising them by value reconstructs the flag exactly from `run.page_url`. (The one theoretical ambiguity, a customer URL that already carries all six `ZINKO-TEST` values, is treated as injected and is not a real-world case.)

### State rules (the engine, in order, per rule)

Notation: for a rule, **B** is the set of cells where the baseline's check result is `fail` (the baseline's failing cells, *all* of them, whether or not they exist now); **C** is the set of cells where the current result is `fail`. A cell is *common* when both audits have a run with the same `CellKey` (`sameCell`), a check result for the rule on both runs, and agreeing `Compat` records for the facts the rule depends on (consent class on accept/reject cells, banner detection for banner-dependent rules under `none`).

1. **Not comparable first.** `rule_changed` (the registry, see Decisions), `rule_added` or `rule_removed` (check results on one side only), `no_shared_scope` (the rule failed or could not be checked somewhere but no cell is common).
2. **Classify every cell of B** by what the current audit says: `pass`, `not_applicable`, `still_fails` (in C), `could_not_check`, `missing` (no run in that cell now, the run failed, or it has no check result), `consent_differs`, `banner_differs`. The counts go into `resolution`.
3. **Decide, in this precedence:**
   - `B ≠ ∅` and the rule **fails on any cell of the current audit** (`C_all`: every cell where the current result is `fail`, common or not) → **unchanged**. `spread`: `narrowed` if some baseline failure is resolved or absent and none fails anew, `widened` if some cell fails only now and none was resolved, `moved` if old failures are resolved **and** new ones appear (including on a page or scenario the baseline did not run), else `same`. Missing or unchecked cells never change the state; they are shown in `cellChanges`.
   - `B ≠ ∅`, **`C_all = ∅`**, every cell of B is `pass` or `not_applicable` → **fixed** (`fixedHow` is `passes` if any is `pass`, else `no_longer_applies`). Fixed never coexists with a current failing cell.
   - `B ≠ ∅`, `C_all = ∅`, nothing `missing`, `consent_differs` or `banner_differs`, and at least one `could_not_check` → **verdict changed** ("can no longer be checked").
   - `B ≠ ∅`, `C_all = ∅`, and some cell `missing`, `consent_differs` or `banner_differs` → **not comparable**, reason `partly_rechecked`, with the counts ("re-checked and passing on 2 of 3 cells; 1 cell was not re-checked"). This is the case the first draft called Fixed.
   - `B = ∅`, `C ≠ ∅` (over common cells): if **every** cell of C was `could_not_check` in the baseline → **verdict changed** ("now fails; was not checkable"); otherwise **regressed** when `earlierFailure` is found (below), else **new**; when some of the C cells were `could_not_check` before, `qualifier = partly_unknown_before` and the row says "was not checkable on 1 of 3 of these cells". A rule failing now only on cells outside the common set, with `B = ∅`, is listed under `outside` and is `no_shared_scope`.
   - `B = ∅`, `C = ∅`: a rule `could_not_check` on one side's common cells and `pass`/`not_applicable` on the other → **verdict changed**; `could_not_check` on both → **unchanged** (kind could not check); otherwise not listed.
4. **Regressed history is cell-level.** For a candidate regression, look at the site's earlier evaluated `full` audits *before the baseline in creation order* (chronological, **not** baseline ancestry, so a branched or re-pointed chain behaves the same), at most 10. Read their `check_result` rows for the rule on the cells of C (matching by `CellKey`). `earlierFailure` is the newest such audit in which the rule **failed on at least one cell of C**, provided the baseline passed or did not apply on those cells and the registry says the rule is comparable between that audit's versions and the current ones. An audit where those cells were unchecked or absent neither confirms nor breaks the chain; a deleted audit is simply absent (a regression whose only witness was deleted reads **new**; one whose witness is kept as a stored marker is not required). An old mobile failure on another page therefore cannot label a desktop homepage failure Regressed.
5. **Confidence.** `volatile_rule`: `ruleId in VOLATILE_RULES`. `flips`: over the last five audits including these two, the rule's fail/not-fail sequence *on these cells* changes at least twice. `single_run`: the change rests on one cell. Low confidence never changes the state; it adds a label and the **Re-check these pages** action.
6. **Triage line.** `before` is the baseline's status (an inherited row counts), `now` the audit's. A baseline `fixed` that still fails reads "Marked fixed on <date>, still fails".

`changesBriefing(comparison)` and `scoreDeltaOf` are pure functions in the same file, used by the Overview and the report builder so both print the same words.

### Tag diff (`apps/web/src/server/compare-data.ts`, `tagDiffOf`)

For each audit, one grouped query: `select run.id, hit.vendor, hit.destination_id, hit.event, count(*) from hit join run … where run.audit_id = $1 and run.org_id = $2 and hit.org_id = $2 and run.status = 'complete' group by …` (the shape of `tagsSeenOf`), mapped to cells in TypeScript with `withoutTestClickIds`. Cells present and `complete` on both sides are *tag-comparable*. Output, capped at 40 tag changes and 10 cells each: `{ change: "disappeared" | "new" | "destination_changed" | "events_changed", vendor, destinationId, previousDestinationId?, eventsAdded[], eventsRemoved[], cellsAffected, cellsCompared }`. Vendors outside the known list are labelled "Other vendor" in the report (the existing `vendorLabel`).

### Re-check targets (`recheckTargets`, pure, `lib/compare.ts`)

`recheckTargets(comparison, ruleId)` returns the rule's B cells and `C_all` cells as `CellKey`s, dropping those the current configuration cannot reproduce; with no comparison it takes the audit's own cells whose `check_result.status` is `fail` for the rule. `narrowedConfig(config, targets)` then builds the config:

- scenarios and viewports are the distinct ones of the targets; if any target has an `itinerary`, pages and `journey: true` are kept whole in their stored order (the capped itinerary is regenerated by the workflow); otherwise pages are the distinct target pages in the baseline's configured order;
- `clickIds` is on only when the audit's start page is among the targets with `injected: true` and stays first; otherwise it is off. Because identity uses **actual injection**, a non-start target (`injected: false`) that becomes the narrow audit's first page with `clickIds` off keeps the same key;
- **banner-detection companions.** `bannerDetection` needs the accept and reject runs of the same page, viewport and journey (`consent-context.ts`: it reads only the audit's own siblings). For every `none` target of a banner-dependent rule, add `accept` and `reject` to the scenarios for that page and viewport; the extra runs are recorded in `narrow_companions`, executed, used for detection, and excluded from every result reader by the narrow-audit projection below. The dialog states "n runs (m extra runs to detect the cookie banner)";
- **verify after building.** `cellsOfConfig(narrowedConfig)` must contain every target `CellKey` (`sameCell`). A target it cannot reproduce is dropped and named in the dialog ("1 page can no longer be re-checked as it was captured"); with **no target left** the action is refused with that message and no audit is created.

The cross product can exceed the targets, so the dialog states the run count. The narrow audit's result is read per target cell: a cell counts only if its run is `complete`, its `Compat` agrees with the comparison's (a re-check whose banner detection or consent outcome differs is incompatible, not a repeat) and it has a check result for the rule. `confirmation.state` is `repeated` when every target reproduces the change, `not_repeated` when every one contradicts it, otherwise `incomplete`.

### The narrow-audit projection (Task 9)

A narrow audit executes more than its targets: banner-detection **companions** and the cross product's **extras**. The workflow evaluates and aggregates every run (`Audit.ts` `persist` and `finish`: `finding` rows and `check_result` are written for all of them), so the readers must project. Contract:

- `createAudit` sets `run.role` for every run of a narrow audit (`target` if its `CellKey` is in `narrow_cells`, `companion` if in `narrow_companions`, else `extra`); every run of a `full` audit is `target` (the column default). The workflow is not changed; it keeps writing check results for all runs.
- **Result readers filter `run.role = 'target'`** in every query that reads runs, hits or check results through a run: `findings-data.ts` (`runs`, `evaluated`, `verdicts`, `outcomes`, `failedDependent`, `reasons`), `audits.ts` (`getAudit`: the run list's result columns, `failingChecks`, `evaluation`, hit counts), `overview.ts` (`runRows`, `checked`), `matrix-data.ts` (`sliceOf`, `tagsSeenOf`), `hits.ts`, `report-data.ts`, `register-data.ts`, `client-summary.ts` (`auditDetails`), `digest-data.ts`/`explain.ts`, `compare-data.ts` and `tagDiffOf`. The score is therefore computed from targets only.
- **`finding` rows of a narrow audit are not trusted.** `finish` aggregated them over all roles, so `findingsOf` for `kind = 'narrow'` rebuilds the findings from the target runs' `check_result` rows with the same grouping as `findingsFrom`, which moves from `workflows/Audit.ts` to a pure `lib/findings-from.ts` that both import (no behaviour change; checked by diffing a full audit's `finding` rows before and after).
- **Companions are kept where they are needed:** `bannerDetection` (`consent-context.ts`) reads **all** roles and is the only reader that does.
- **Counting what ran.** Admission, the cap, the estimate, the progress header ("x of y runs"), the room events and the site history's run counts use **all executed runs**; the Runs list shows every run, with a "Banner check" or "Extra" badge on non-targets and no verdict column for them. Result surfaces use targets.
- **Not reported.** A narrow audit has no Report tab content ("Re-checks are not reported") and no register.

## Report: `changes` (Task 11)

```ts
changes: null | {
  baselineDate: string                                   // ISO; reportDate
  counts: { new: number; regressed: number; fixed: number; unchanged: number; verdictChanged: number; notComparable: number }   // after exclusions
  omitted: number                                        // changed findings left out of the detail; no states, no titles
  score: { before: number | null; now: number | null; delta: number | null }
  items: { ruleId: string; state: "new" | "regressed" | "fixed" | "verdict_changed"; severity: Severity; title: string; pages: number; pagesCompared: number
           confidence: "normal" | "low"; confirmation: "none" | "repeated" | "not_repeated" | "incomplete"; qualifier: "partly_unknown_before" | null }[]   // 12
  tags: { change: "disappeared" | "new" | "destination_changed" | "events_changed"; vendor: string; destination: string | null; events: string[]; cellsAffected: number; cellsCompared: number }[]  // 8
  notices: ("rules_changed" | "scope_differs" | "banner_differs" | "consent_differs" | "score_not_comparable")[]
  lines: string[]                                        // the briefing, built from the projected items only
}
```

- **Exclusions first.** The current audit's `report_finding_edit.hidden` set (own or inherited) is applied **before** anything is counted or worded: a hidden rule contributes nothing to `items`, `lines`, `counts` or `pages`; it adds one to `omitted`. A baseline-only (fixed) finding is hidden when the current audit's edits hide that rule id (a carried "leave out" does), and is otherwise shown with the baseline's stored title. **The writer must allow it:** `saveFindingEdit` today requires a current `finding` row (`report-edit.ts`), and a fixed rule has none. It now takes `{ auditId, ruleId, against? }` and authorizes the edit against either the current finding or, with `against`, an authorized comparison (both ids through `auditInOrg`, same site, `against` older, the rule present as a finding of `against` and absent now) using the baseline's stored wording; the row is keyed by the current audit and rule id as before. The Compare row of a Fixed change and the consultant view's dimmed list get the "Leave out of the report" action. Amend the `AGENTS.md` invariant that a finding edit needs a finding of the audit. `tags` and `notices` do not name findings. The consultant view still shows hidden changes dimmed, from the consultant side payload only, as M5 does.
- **Qualification is part of the claim.** An item with `confidence: low` and no repeat reads "may be a flaky result" in the lines, in the item and in the printed report; `not_repeated` reads "did not repeat on re-check"; `incomplete` reads "re-check incomplete". The qualification is frozen with the item, so a snapshot never upgrades itself when a confirmation arrives later; a later confirmation shows as "Unpublished changes" on the draft.
- **Two different hashes, kept apart.** *Race detection* is `ReportStamp` (`readStamp`, compared under the publication lock; a difference sends publication back to the read, at most three times). *Reuse* is the model's `publicationHash` (identical model, identical logo bytes, same snapshot). A stamp change that leaves the model identical therefore does not create a version; a model change does. `ReportStamp` gains one field, `comparison`: an `md5` fingerprint, in the `rowsOf` style, of the **ordered dependency list** the comparison read: the baseline id and its `finished_at`; the ids and `finished_at` of the regression-history audits that were selected, in order; the ids, `narrow_rule_id`, `narrow_cells` and `finished_at` of the confirmations that were selected; the baseline's `finding_triage` rows as **full-row text** (`rowsOf`-style, so `status`, `reason`, `updated_by`, **`updated_at`** and the `inherited_from_*` markers are all in it: the wording "Marked fixed on <date>" is read from `updatedAt` through `triageOf`, so an identical-value re-save changes the wording and must change the fingerprint); the current audit's own triage and edits are already covered by `readStamp`'s existing full-row fingerprints. A count plus a latest time would not tell which audits were chosen; ids and values do.
- Validators (`LEAF_VALIDATORS`): `count` for every number, `nullable(amount)` for scores, `date`, `oneOf` for state, tag change, notice, confidence, confirmation and qualifier, `stored` for titles, `vendorLabel`, `nullable(destinationLabel)` at the report's detail level, `event`, and `stored`-bounded text for `lines` built only from those leaves. No page names (pages are counted: aliases mean different pages in two audits).
- **Versions.** `REPORT_MODEL_VERSION` 3 becomes 4. `ReportModel.modelVersion` is `Schema.Literals([1, 2, REPORT_MODEL_VERSION])`; list every historic version (`[1, 2, 3, REPORT_MODEL_VERSION]`) or stored version 3 stops decoding. Add `UPGRADES[3]: (json) => ({ ...json, changes: null })`. The chain must be verified from **stored versions 1 and 2** as well (`UPGRADES[1]` and `[2]` run, then `[3]`).

## Security

- Both ids of every comparison go through `auditInOrg`; the second must be on the first's site and older; any failure is the same 404 as a missing id.
- `rerunAudit`, `recheck` and `setBaseline` take audit ids (and a rule id), never a config from the client: the config is read from the stored audit and re-validated by `AuditConfig` and `normalizePages`. A foreign audit is a 404; an archived site gives the existing message.
- Any member may re-run, re-check and set the baseline; the organization advisory lock, the cap and the in-progress guard bound abuse.
- Carry-over copies only rows of the source audit selected with `org_id`, inside the creation transaction.
- Report `changes` is built from stored static wording and counts only, projected through exclusions, and checked by `assertProjected`; the M5 hostile seed is extended in Task 12 with a baseline whose tag events, destinations, reasons and notes carry hostile strings and with hidden findings of every state.
- **Demo (only if gate Q7 is answered yes).** A deny-by-default design, specified in Task 17: an explicit `mutation` gate on every state-changing path (not `respond`, which `read()` also calls), enforced for future code by the Task 15 registry check in `pnpm check`, a deny-by-default Better Auth route policy, and a runtime composition without a capture engine.

### Task 15: The entry-point registry and the mutation gate

**Model:** Opus
**Files:** `apps/web/src/server/entry-points.ts` (the registry), `scripts/check-entry-points.mjs` (plain Node, no dependency), root `package.json` (`check` runs the script before `vp check`), `apps/web/src/server/server-fn.ts` (`mutation`), every state-changing server function (`respond` becomes `mutation`; `ai-settings.ts` and `run-browser.ts` stop calling `runtime.runPromise` directly for writes), `AGENTS.md` (the rule), `docs/decisions/0005-demo-data.md` (the inventory table)
**Interfaces:** the registry, the route metadata, `RUNTIME_ALLOWED` and `mutation`, checked by a script that `pnpm check` runs before `vp check`.

**The check script is a static analysis with the TypeScript compiler API** that is already in the repo (`typescript` is a catalog dependency of the root and `apps/web`; no new dependency). It uses `ts.createSourceFile` (syntax only, no program, no type check) over `apps/web/src/server/**/*.ts` and never imports an application module. Contract:

- **Names are resolved through imports.** For each file it records the local name of each import (`createServerFn` from `@tanstack/react-start`, `runtime` from `./runtime`, `Effect` from `effect`, `mutation`, `read` and `respond` from `./server-fn`), including `as` aliases and namespace imports, and matches calls against the resolved names, not the spelling.
- **Server functions.** An exported `const` whose initializer is a call chain rooted at the resolved `createServerFn`; `method` must be a string literal in its first object argument; the `.handler(...)` argument is searched (AST, so multiline) for calls to the resolved `mutation`, `read` or `respond`. Rules: every such export is in `ENTRY_POINTS` and every entry exists; `mutation` entries are `POST` and call `mutation`; `read` entries are not `POST` and call neither `mutation` nor `respond` directly.
- **Runtime calls.** Any `CallExpression` whose callee resolves to `<runtime>.runPromise` / `runPromiseExit` / `runFork`, `Effect.runPromise*`, `Effect.runSync*`, `Effect.runFork`, or a `ManagedRuntime` use, in a file outside `RUNTIME_ALLOWED`, fails, however the call is formatted or aliased (`import { runtime as rt }`, a `const r = runtime`, a call split across lines).
- **Worker routes.** `routes.ts` is parsed for the `workerRoutes` array; each element must be an identifier imported from a file under `server/` (a spread, call, conditional or other expression is **unsupported syntax and fails**). The imported file must declare, next to the route, a static literal `export const <name>Meta = { path: "<pattern>", methods: ["GET", ...], access: "read" | "mutation" } as const` (an object literal of string literals only; anything else fails). `ENTRY_POINTS` classifies server functions only; the routes classify themselves and the script checks each: `access: "read"` requires `methods` within `GET`, `HEAD` **and** a method guard in the route's code (a comparison of a `.method` property with a string literal that returns `undefined` or a 405); `access: "mutation"` requires that the route is `/api/auth/*` or calls `mutation`. `auditRoomRoute` (the WebSocket upgrade at `/ws/audits/*`, today with no method restriction) is `read`, `methods: ["GET"]`, and must gain the guard; the Better Auth route is `mutation`.
- **Unsupported syntax fails closed**: `createServerFn` stored in a variable and reused, a re-export of it, a computed `method`, a dynamic `import()` of a server module, a non-literal meta, an element of `workerRoutes` it cannot resolve. The message names the file, line and the supported form.

`ENTRY_POINTS: Record<"<file>.<export>", "read" | "mutation">` classifies server functions; `RUNTIME_ALLOWED: string[]` lists the files that may call the runtime (`server-fn.ts`, `session.ts`, `require-session.ts`, the Worker route files, `auth-live.ts`, `invitation-email.ts`, the mailer-side runtime). `mutation(effect)` is `respond` plus a gate that, in demo mode (Task 17) and for the demo organization only, refuses before any side effect; outside demo mode it is `respond`.

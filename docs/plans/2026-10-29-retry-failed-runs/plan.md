# Retry Failed Runs Plan

**Goal:** "Retry failed runs" on a finished audit creates a new full audit that reuses the original's good captures and captures only the cells that failed for a reason worth retrying (or only re-saves results when the sole problem was a failed database write and no cell needs the browser). The new audit is complete, scored, comparable and reportable like any other, and it says which of its results were captured on which days and which were reused. Demo: an audit of a fixture with the capture engine stopped half way ends Partial with `EngineBusy` runs; after the engine is back, "Retry 4 runs" starts an audit whose other runs finish in seconds without touching the engine, the 4 failed cells go through the capture queue, the new audit ends Complete with the original as its baseline, the report prints the capture date range and "24 of 28 results reused from the audit of 28 Oct", and Compare shows reused cells as unchanged against the original and never as a change against a later audit.

**Approach:** A retry is a re-run with a seeded run list. `createAudit` gets an origin `retry` (same stored config, baseline = the original, everything else as a re-run: carry-over, cap, one in progress per baseline). It resolves, for every cell, the immediate source run in the original audit and snapshots what is needed to copy it onto the new run row. In the `Audit` workflow a reused run takes a crash-safe `reuse-<n>` step that copies the source's capture objects to the new run's own keys, then goes through the existing `persist-<n>`: hits, pushes and check results are rebuilt from the copied capture under the current decoders and `RULES_VERSION`, with `created_at` from the source run's original `finished_at`. Reused runs never ask the capture gate. A reuse that cannot be done falls back to a normal capture. Compare gets an explicit chronology rule for observations older than the thing they are compared with. The report and the CSV disclose capture dates and reuse. Three nullable columns on `run` and two on `audit`, one migration, a report model bump.

**Effort (after review r7):** the table in Tasks adds up to 29.5 working days including Task 0's day (done): 28.5 remain, of which Task 3a (4.25 days) ships first and alone; plus 1.5 to 2.5 days for the deployed smoke gate (Task 12), which is no longer blocked (the app is deployed on a Cloudflare workers.dev stage). Reviews r3 to r6 added about 9 days to the 19 that remained: supersession retrieval, witness rules, batched loaders and the request-derived stamp (Task 6), the atomic fallback (Task 4), browser-work accounting (Tasks 3, 8, 10) and the lifecycle fence and reconciliation (Task 3a). The scope is recovery of an **evaluated partial audit**: it is not a database-outage recovery tool (an audit in which nothing was persisted is unevaluated and stays out of v1).

## What a "failed run" is today

- **Failed without a result** (`run.status = failed`, `run.failure` set by `fail-<n>`): `EngineBusy`, `EngineFailure`, `PersistFailure` (the capture is stored, only the database write failed; `run.engine` is null for it). `failure = null` with `failed` is a refused request (`PolicyDenied`, `InvalidRequest`). `fail-<n>` sets `finished_at` even though there is no capture.
- **Partial with a capture** (`run.status = partial`, `run.complete = false`): `run.errors` lists `BotBlocked`, `Timeout`, `Navigation`, `HttpStatus`, `JourneyStep`, `EngineFailure`, `CmpNotFound` or `ConsentNotApplied`. The Overview counts these in "n of m runs could not finish", including a `CmpNotFound` run on a site with no banner, which is an observation, not a failure.

So the notice's count is not the number of runs worth capturing again. The button says "Retry 3 runs"; the dialog says why the rest are kept.

## Decisions (proposed; the owner may overrule)

1. **A retry is a new full audit, made by `createAudit`.** Origin `{ kind: "retry", auditId }` behaves as a re-run: stored config, baseline = that audit, the same carry-over (`copyCarryOver`), the cap of five active audits and the one-in-progress-per-baseline guard (a Retry and a Re-run of the same audit exclude each other; the message names both). Because it is a normal audit, chronology by `createdAt`, re-checks, publication stamps (`readStamp` fingerprints this audit's own `finishedAt`), the cap and the guards work as they do. No audit is ever reopened. (r3) A retry stores the origin's **complete stored config verbatim** (the JSON in `audit.config`, whether or not `clickIdPages` or any other optional key is present; nothing is defaulted, normalised or re-derived), and every `CellKey` is computed per side from that audit's own stored config with the current `cellKeyOf` (the click-ID task changes its inputs), so a legacy start-only audit and an audit with injected key pages both keep their cells.
2. **What is reused and what is recaptured.** Cells are matched by `cellId(cellKeyOf(run, config))` plus the follow host.
   - **Recaptured:** a run with no usable capture and a retryable failure (`EngineBusy`, `EngineFailure`); a partial run whose **first** error is retryable: `Timeout`, `EngineFailure`, `HttpStatus` 429 and 5xx, and a `Navigation` error whose text is a start-page load timeout (`Timeout <n>ms exceeded`, `ERR_TIMED_OUT`) or "no response" (`ERR_EMPTY_RESPONSE`, `ERR_CONNECTION_RESET`, `ERR_CONNECTION_CLOSED`). (Task 0: a refused port arrives as `ERR_EMPTY_RESPONSE`, so refused and a transient reset cannot be told apart and both are retried; a heavy page whose `load` never fires within the 30 s `goto` timeout is a `Navigation` timeout and will usually fail again.)
   - **Reused:** every run with an intact capture that is not recaptured: complete runs; partial runs with a deterministic problem (404 and other 4xx, off-site redirect, `BotBlocked`, `JourneyStep`, `CmpNotFound`, `ConsentNotApplied`); and `PersistFailure` runs (the stored capture is fine; reusing it is the persistence-only repair). (Task 0: "DNS, refused, certificate" are removed from this list: an unresolvable host is refused by the engine as `PolicyDenied` and never becomes a partial run, a refused port is `ERR_EMPTY_RESPONSE` (above), and an expired certificate is captured `complete`. `NETWORK_ERRORS` keeps its patterns for wording, but only the timeout and no-response patterns decide a retry.)
   - **Ordinary path:** a refused run (`PolicyDenied`, `InvalidRequest`; no capture, `failure` null) has nothing to copy; it is created as a normal pending run and goes to the engine like any run, which refuses it again at once unless the cause was transient (an unresolvable host is `PolicyDenied: could not resolve`). (Task 0) Ordinary-path runs are not counted as "recaptured", never make a retry eligible by themselves, and do not appear in the button's number; they ride along when the retry is made for another reason. (r3) They are **browser work**: the engine is asked for each, so they count in the estimate, in the start-page preflight decision and in the admission queue (Decision 9), and the preview reports them separately (`ordinary`). Any other `failed` run with no capture and no known failure (one legacy row has `failure` null, empty `errors`, `complete` true) takes the same path.
   - (Task 0) **The classifier keys on `failure`, `capture_key` and the first `errors[0]`, never on `run.engine` or `run.complete`.** A `PersistFailure` run has `engine` null only when `persist` failed before its transaction; when a later step failed, `run.engine`, `consent` and `complete` stay from the commit while `fail` zeroes `hit_count` (2 of 3 real rows are like this).
   - (r3) **`ReuseFailure`** (Decision 7.6) is a `failed` run with no capture and no copy state (its `fail-<n>` clears keys and provenance atomically, below), so the classifier treats it as **recapture**: it counts in "Retry n runs", and the next retry resolves its source cell to a run without a capture and captures it normally. A run that still holds `reuse_plan` or a destination key after a terminal failure is a defect, not a class.
   - (r5) **`Interrupted`** is the failure Task 3a gives a run of an audit that stopped (its workflow ended or went silent) before the run finished. It keeps whatever the run had: **with** a stored capture (`capture_key` set, `finished_at` = the capture time) it is a persistence-only repair, classified **reuse** like `PersistFailure` (a retry copies the capture and re-evaluates it); **without** a capture it is classified **recapture**. Text: "The audit stopped before this run finished" (`FAILURE_TEXT.Interrupted`), never "The browser engine failed".
   - A recaptured partial run is not "kept if worse": a new audit records what was observed in it, and the original still holds the earlier result as its baseline.
3. **Copy the capture objects from the immediate source; do not reference.** The source of a cell is found through `audit.retry_of_audit_id` plus the cell's `CellKey` in that audit (never through `reused_from_run_id`). Its `capture_key` and `screenshot_key` are what is copied; if the source itself was reused, those are its own copies, so the chain never needs the root. `reuse-<n>` reads them with `Storage.get` and writes the new run's own keys (`audits/<newAudit>/runs/<newRun>/...`) with `Storage.put`, so the new audit owns its objects and every reader keeps working from `run.capture_key`. Referencing was rejected: no reference counting, and deleting the original audit would break the retry's evidence. The cost is duplicated storage; Task 0 measures real capture and screenshot sizes. No new `Storage` method.
4. **Reused runs are re-evaluated, not copied as results.** The copied run goes through the existing `persist-<n>` with current decoders and `RULES_VERSION`; `created_at` = the new run's `finished_at`, which `reuse-<n>` sets to the **source's** `finished_at` (never `now()`), so a replay writes identical rows. `finish` is unchanged. The audit is judged by one rules version and one decoder version.
5. **Provenance (columns).**
   - `run.reused_from_run_id uuid null`, no FK: the **root** run that made the capture (`source.reused_from_run_id ?? source.id`). Capture identity only; the row it names may not exist.
   - `run.reuse_plan jsonb null`: written by `createAudit` in its transaction from the source row: `{ sourceRunId, captureKey, screenshotKey, finishedAt, captureFormat }`. This is the durable snapshot the copy step uses, so a replay never re-resolves a source that may have changed. Cleared on fallback.
   - `audit.retry_of_audit_id uuid null` and `audit.retry_of_at timestamptz null` (the original's `created_at`), no FK, independent of `baseline_audit_id`.
   - A fallback clears `reused_from_run_id` and `reuse_plan` (the run then really was captured in this audit).
6. **A Zinko-owned capture format, not engine strings.** `CAPTURE_FORMAT` (an integer in `@repo/capture-contract`) is written into `capture.json` by the `capture` step (an optional field of the stored capture schema; captures stored before it are format 1). `MIN_REUSABLE_FORMAT` (next to it) is the oldest format whose facts the current rules and decoders need. It is raised, together with `CAPTURE_FORMAT`, in the same change that makes a rule or decoder need a fact the capture did not previously carry; this goes into the "To add a rule" checklist in `AGENTS.md`, worded to cover a **decoder change** and a **changed existing rule** as well as a new rule (r3, owner answer to question 2). The check reads the stored capture's own field after decoding it (so a `PersistFailure` run, whose `run.engine` is null, works), never a third-party engine or library version. A reuse below the minimum falls back to a normal capture. Older `RULES_VERSION` or decoder versions never block reuse: captures are re-evaluated, and rules whose verdict can differ are marked Not comparable against the original by `RULE_CHANGES`.
7. **Crash-safe copy protocol (`reuse-<n>`).** One step per reused run, all of it idempotent:
   1. Read the run. If `capture_key` is set and both destination objects exist (`head`; the screenshot only if the plan names one) and `finished_at` equals `plan.finishedAt`: the destination is complete, return `Reused` without touching the source (recovery after a crash after the row update). If `capture_key` is set but a destination object is missing, the destination is incomplete: go to step 2, and if the source cannot supply it, to the fallback.
   2. Otherwise check the source from the plan: `head` of the capture and screenshot, `get`, `decodeStoredCapture`, `captureFormat >= MIN_REUSABLE_FORMAT`. Any failure, or a source run/object that is gone, goes to the fallback.
   3. Copy the screenshot first, then `capture.json` last (the invariant `capture` already relies on: a stored `capture.json` means its screenshot is stored). `head` both afterwards and compare sizes with the source.
   4. One row update, in a transaction whose first statement is the audit fence: `capture_key`, `screenshot_key`, `finished_at = plan.finishedAt`, nothing else; fenced means the step ends `Fenced` and the copied objects stay as unreferenced orphans under the run's own prefix (never deleted by this step). Then `persist-<n>` (existing).
   5. Fallback (r3, r7): a **fenced detach before any deletion**. (a) One transaction whose first statement is the audit fence (Task 3a, section 1) and that then, in the same transaction, sets `capture_key = null`, `screenshot_key = null`, `finished_at = null`, `reused_from_run_id = null`, `reuse_plan = null`, `status = 'pending'` on the run and inserts the destination keys into `run_cleanup (run_id, org_id, keys)` (a new table in this plan's migration, `run_id` referencing `run` with `on delete cascade`): the cleanup intent is recorded in the same commit that detaches the references. If the fence returns no row the step ends `Fenced` and **deletes nothing**: a settlement that kept this run as `Interrupted` with its capture keys keeps pointing at objects that still exist. (b) After the commit: delete `capture.json` first, then the screenshot, then the `run_cleanup` row. (c) Then the run joins the normal `admit` and `capture` loop. A crash after (a) leaves the keys detached and the cleanup row present; the replayed step, and `capture()` for that run before it writes anything, finish (b) first. The keys must go in the same update as the provenance because `capture()` returns `Stored` for any run whose `capture_key` is set; and the objects are deleted only after nothing references them, because the new capture will be written at the same keys. No state exists in which a reference survives its object, or an object is removed while a settled row still points at it.
   6. Storage and database errors retry under the normal step policy; if the step is exhausted, a `reuse-fallback-<n>` step runs the fallback; if that is exhausted too, `fail-<n>` records the run with a new failure `ReuseFailure` ("Results could not be copied", in `FAILURE_TEXT`) and, in the same transaction as the failure, performs the fenced detach of 5(a) (keys, `finished_at` is then set by `fail` as for any failed run, provenance and plan null) and, after the commit, deletes the destination objects through the same `run_cleanup` row; an object it cannot delete is an orphan under the run's own key prefix, which nothing reads because `capture_key` is null. The audit goes on and the run is retryable (Decision 2).
8. **Compare: the exact chronology rule.** Definitions. Every `CellRun` gets `captureId` (`reused_from_run_id ?? run.id`) and `observedAt` (the `finished_at` of the run that owns the capture; a reused run keeps the source's; runs without a capture, such as `fail-<n>`, have none and are "missing" as today). For a comparison of `now` (the audit shown) against `before`, per cell present on both sides:
   - **same**: `captureId` equal. One observation seen twice. Not a change and not evidence of persistence.
   - **older**: different `captureId` and `now.observedAt < before.observedAt`. The audit shown holds an observation older than the one it is compared with. It must not imply a new failure, a fix, a regression or a persistent failure.
   - **fresh**: anything else (different capture, `now.observedAt >= before.observedAt`).
   
   Cells of class older are left out of `commonCells` and listed with a new resolution `older_observation` ("Captured before the audit it is compared with"). Cells of class same stay common. Then the existing machinery decides, with these consequences per change kind:
   - **New / Regressed** (fails now, did not fail before): a failing cell that is older is not counted among `fresh` or `failsNowCommon`. If no failing cell remains, the finding is Not comparable with reason `older_observation` ("These results were captured on 28 Oct, before the 29 Oct audit it is compared with, so they cannot show a new problem."). This is the reviewer's probe: C (retry of A) against B no longer reports Regressed.
   - **Fixed** (failed before, passes now): a passing cell that is older is `older_observation`, not `pass`. It cannot fix a failure observed later. If every cell that settles the finding is older the state is Not comparable `older_observation`; if some cells are fresh and pass, the existing logic applies to those and the older ones are counted in `partly_rechecked` as today's `missing` cells are.
   - **Unchanged** (fails before and now): older failing cells do not count as "still fails". Unchanged requires at least one fresh or same failing cell on a comparable pair; a same-capture failing cell does count (it is the original's own observation), so a retry compared with its original keeps "Unchanged". If every failing cell is older: Not comparable `older_observation`. Spread (`narrowed`, `widened`, `moved`) is computed on non-older cells only.
   - **Verdict changed** (to or from Could not check): cells that are older are excluded; if nothing is left the finding is not listed.
   - **Not comparable** reasons that exist today (rule changed/added/removed, no shared scope, partly rechecked) keep their precedence over `older_observation`.
   - **Reinterpreted** (finding 6): a **same**-capture cell whose stored verdict differs (current decoder or rules re-evaluated the copy; the original's rows keep their old rules version) is never a Fixed/New/Regressed: it gets resolution `reinterpreted` and, when it would decide the state, Not comparable `reinterpreted` ("Judged again by newer checks"). This separates a site change from a reading change. The existing compatibility checks stay: `compatDiffers` (consent class, and banner detection, which is derived from sibling runs and may differ when siblings were recaptured), `ruleChanged`, `decoderVersionsDiffer`, changed measured hosts (a cross-host cell the site no longer declares is outside scope, as today).
   - **History windows (r3).** Two limits exist today and neither counts captures: `comparisonOf` loads the ten audits created before the baseline (`HISTORY_AUDITS`, `older`), and `flipsOf` then keeps only `FLIP_AUDITS - 2` = 3 of them. Retries make the same capture appear in several audits, so duplicates would crowd genuine observations out. Change: `comparisonOf` loads up to `HISTORY_SCAN` (60) audits before the baseline, `historyOf` returns them, and a new step `distinctObservations` (in `lib/compare.ts`) deduplicates **per cell by `captureId`** and orders by `observedAt` descending **before** `HISTORY_AUDITS` (10, for `earlierFailureOf`) and the flip window (`FLIP_AUDITS`, for `flipsOf`) are applied. `earlierFailureOf` skips a witness with the same `captureId` as the current or the baseline cell and counts a witness only if `witness.observedAt < baseline cell.observedAt`; `flipsOf` builds each cell's answer sequence from the deduplicated observations, one answer per capture. If the scan limit is reached the search stops there (as the ten-audit limit does today): a regression can then read New instead of Regressed, never the reverse. (r4) The scan widens to 60 only when the compared pair has a reused cell or one of the scanned audits has `retry_of_audit_id`; every other comparison keeps the ten-audit scan and today's results. **Loader, batched (r4):** today `historyOf` runs `cellRunsOf` (a run query plus a `bannerDetection` query) per audit, twice per comparison (a first pass for changed rules and a second with the history): up to 244 queries and 10,080 target runs per pass for 60 audits of 168 runs, inside the report's read transaction. Change: (1) `historyOf` reads the target runs of all scanned audits in **one** query (it already selects `run.id, run.auditId`; extend it with the `cellRunsOf` columns) and the banner inputs in **one** bulk query (`bannerDetection` takes `auditIds` and returns a map by run id), and builds each audit's `CellRun`s in TypeScript; (2) `comparisonOf` loads the history **once**, for every rule that fails or is inconclusive on either side, and both `compareAudits` passes reuse it; (3) `distinctObservations` drops duplicate captures before the check rows are filtered. History is therefore a constant number of queries (about 6) however many audits are scanned. **Cost gate:** see the 60-audit probe in Task 6.
   - **Confirmations (re-checks) (r3).** Three exclusions in today's code hide a re-check made between the original capture and the retry: (1) `comparisonOf` loads confirmations only for `changed` findings (`state` not `unchanged` or `not_comparable`) and `compareAudits` computes `confirmationOf` only when `judged`; (2) `confirmationsOf` loads narrow audits created after the audit shown (`(created_at, id) > (select ... where id = auditId)`), so a re-check R that finished before the retry C was created is never read; (3) `comparisonStampOf` fingerprints re-checks created after the audit with the same predicate. Changes: a finding with **any reused cell** (a cell whose `captureId` differs from its run id) is loaded and judged for confirmation whatever its state, including `unchanged` (expectation: fails, as the stored verdict says); `confirmationsOf` takes an `observedFloor` (the earliest `observedAt` of the reused cells of the changed findings) and selects narrow audits of the rule with `finished_at > observedFloor` instead of the creation predicate when the audit has reused cells (the creation predicate stays for audits without reuse); the stamp uses the same floor, its `rechecks` digest (id, rule, state, cells, finish time) covers every narrow audit of the site finished after the floor, and a re-check finishing during publication changes `status` or `finishedAt` and so the digest. (r6) The loader and the stamp's re-check digest are narrowed to the actual dependencies: only narrow audits whose `narrow_rule_id` is the rule of a judged finding **and** whose `narrow_cells` (compared by `cellId` with each audit's own config) contain a changed cell of that finding enter `confirmationsOf` and the digest (any status, so a running re-check turning terminal changes it); a re-check of another rule or another cell never invalidates a publication. For comparisons without reuse the legacy loader and digest are unchanged. A re-check counts for a cell only if its target run's `captureId` differs from the audit cell's and its `observedAt` is later than the audit cell's. The confirmation carries `observedAt` (the `finished_at` of its latest confirming target run) as a new field of `FindingChange.confirmation`; the UI shows "Re-check, 29 Oct: did not repeat" and the report's `changes` item gets a UTC `date` for it, with a validator in `LEAF_VALIDATORS` (a model field of version 10).
   - **Tags.** `tagSideOf`/`diffTags` take the same per-cell classes: a tag seen only in an older observation is not "New", and one missing only from an older observation is not "Disappeared"; same-capture cells compare equal; the "runs compared" figure counts only non-older cells. (r3) Tags are not rule-specific, so a cell is **superseded for tags** when the superseder search below finds a different complete capture of the same cell in the window, whatever the rule; those cells are left out of the tag comparison like older ones.
   - **Score.** `scoreDeltaOf` shows no delta when any compared cell of a listed finding is `older_observation` or `superseded_observation` (a `Comparability` count for each) and says why: "Some results are older than the audit compared with" / "Some results were already changed by a later capture".
   - **Stamp (r6).** `comparisonStampOf` fingerprints, for the audit and every audit or re-check the comparison read, the target runs' `(run id, captureId, observedAt)` in addition to what it reads today; and the **witness dependencies derived from the actual comparison requests**. A shared function `witnessRequestsOf(before, now)` in `lib/compare.ts` produces them and is used by both `comparisonOf` (to call `witnessesOf`) and the stamp, so the two cannot diverge: the set of `(CellKey, ruleId)` pairs such that the cell is **reused on either side** (the audit's cell or the baseline's: fresh D against reused baseline C counts) and the rule fails or is inconclusive on that cell on either side, each with its window `(earlier observedAt, later observedAt]`. The digest then contains only: (1) **non-terminal** audits of the site (`queued` or `running`; at most five per organization) whose own stored config covers the pair's `CellKey` (full audits, by `cellsOfConfig` and `cellId`) or that are narrow audits with `narrow_rule_id` = the pair's rule and `narrow_cells` containing the `CellKey`, as `(id, status, finished_at)`; (2) **terminal** audits' target runs matching the **same SQL predicate `witnessCandidate`** as `witnessesOf` within the pair's window (so every row that can consume the witness budget is fingerprinted, and none that cannot is), and, for narrow audits, the rule, as `(run id, audit id, audit.status, audit.finished_at, run.status, run.finished_at, consent outcome, decoder_version, md5 of that run's check_result rows for the pair's rule)`. Another page's audit, an unrelated full audit and a narrow re-check of another rule are in neither set. Empty (and unchanged from today) when no pair exists, which is every comparison without reuse.
   - (Task 0, rewritten r3) **Superseded observation.** The classes above only handle a `now` cell older than its `before` cell. The probe showed the opposite: D, started after the retry C, compares with C by default (`latestBaseline` orders by `createdAt`) and reports **Fixed** although B had already passed before C existed. Rule: a pair of cells with different `captureId`, where at least one side is reused and `before.observedAt <= now.observedAt`, is **superseded** when a *witness* exists:
     - **Where it is found (independent of `HISTORY_AUDITS` and `FLIP_AUDITS`; one batched query, r5).** A new `witnessesOf(orgId, siteId, requests)` in `server/compare-data.ts` is called **once per comparison** with a request for every judged finding that has a reused side: `{ ruleId, cell (scenario, viewport, cellId), oppositeVerdict, after: before.observedAt, upTo: now.observedAt, excluded captureIds }`. One SQL statement joins target runs with a capture (`run.role = 'target'`, `run.capture_key is not null`, `run.complete`) of **terminal** audits (below) to `check_result` and to the request list (`values (...)` rows matched on rule id, scenario, viewport and verdict), with `run.finished_at > after and <= upTo`, ordered by `run.finished_at`, in pages of 1500 rows, **at most 2 pages per comparison** (a request-wide bound of 3000 candidate rows). **Structurally unrelated cells are excluded in SQL, before the budget (r7)**: the request join also matches `run.scenario`, `run.viewport`, `run.journey`, `run.follow_host` and the page, **derived with the same configured-page semantics as `cellKeyOf`** (r8): for a non-injected run `run.page_url` equals the cell's page (the full normalised URL **including its configured query parameters**, as `normalizePages` stores it); for an injected run the page follows **the candidate audit's own stored config, as `cellKeyOf` does** (r9): when the config has `clickIdPages`, an injected run belongs to the one configured page (`config.pages[pageIndexOf(pages, run.pageUrl)]`, which may be a key page such as `/checkout?market=uk`, not only the start page) and the predicate compares the run's URL with that configured page **plus the six test click-ID parameters** (`injectionOf`); a legacy config without `clickIdPages` injected the start page only, so it keeps the start-URL semantics. The request therefore carries, per candidate audit, its resolved configured page under both rules, and the predicate is never a prefix cut at `?` and never the query stripped from both sides; two pages that differ only in a configured query (`/checkout?market=uk` and `/checkout?market=de`) are different pages and cannot consume each other's budget, through one shared predicate `witnessCandidate(request)` that the stamp reuses, so a row on another page can never consume the budget. The remaining rows are then matched to requests in TypeScript by the exact `cellId(cellKeyOf(run, thatAudit's config))` (this only drops same-page rows with a different itinerary), `ruleChangedBetween` and `compatDiffers`; the first surviving row per request is its witness. A request still unanswered when the cap was hit before the window was exhausted gets `insufficient_history` (next bullet); one whose window was exhausted without a witness is simply not superseded. Comparisons with no reused side make no query, so audits with no reuse are untouched.
     - **Terminal audits only (r5).** A witness comes only from an audit whose status is `complete` or `partial`: a full evaluated audit, or a narrow audit whose `narrow_rule_id` is the rule and whose `narrow_cells` contain the cell. A `queued`, `running` or `failed` audit is never a witness, even if one of its runs already finished with a passing result. This settles the sibling inputs of `compatDiffers`: `bannerDetection` reads the accept/reject companion runs of the same audit, and they are all settled once the audit is terminal, so a companion cannot change banner compatibility afterwards. An in-flight witness is not considered at all.
     - **Overflow is its own reason (r4, r5).** If the request-wide cap (2 pages) is reached before a request's window is exhausted and no witness survived for it, the finding is Not comparable with reason `insufficient_history`, wording "Not compared: too many later captures of this cell to check against." (no date, no claim about what they show). It is never reported as `superseded_observation`, whose wording ("had already changed") needs a witness that differs. `insufficient_history` is carried like the other reasons: `Resolution`, `NotComparable`, tags (cell left out), `Comparability` count and the score note, the report's `changes` section with a validator, and the stamp.
     - **What counts as a witness (rule-specific, trusted).** A `check_result` of the same rule, status `pass` or `fail` (not `inconclusive`, not `not_applicable`), from a run with `complete = true`, whose `captureId` is neither the `before` nor the `now` cell's, judged by a rules version that `ruleChangedBetween` accepts together with the compared versions, and compatible with the cell it would supersede (`compatDiffers(ruleId, witnessRun, comparedRun, bannerDependent) === null`; consent class and banner agree). Its verdict must **differ from the `before` verdict** (a witness that fails like `before` shows nothing had changed, so `Fixed` stays valid). A bot challenge, a partial capture, an incompatible consent outcome or a Could not check never supersedes: B in the review's example does not suppress D's Fixed. A narrow re-check is a witness for its own rule and its target cells only.
     - **Precedence per cell.** `same` (equal `captureId`) first, then `older_observation`, then `superseded_observation`, then `fresh`. Among finding states, today's not-comparable reasons (rule changed, added, removed, no shared scope, partly rechecked) keep precedence over both new reasons.
     - **Reason and wording.** A separate reason `superseded_observation`, not reusing `older_observation`: "A later capture of this cell, from the audit of 29 Oct, had already changed." (the date is the witness's UTC day; the audit is named only by its date). It is applied the same way to findings (`Resolution`, `NotComparable`, `FindingChange`), tags (above), score comparability (`Comparability` count and the `scoreDeltaOf` note), the report's `changes` section (wording and `LEAF_VALIDATORS` for the reason and its date) and the publication stamp (candidate set above).
     - **Alternative rejected:** ranking default baselines by observation time would make a retry never the baseline of anything.
   - **Readers that change (r3, by name):** `lib/compare.ts`: `CellRun` (+`captureId`, `observedAt`), `Input` (+`superseders`), `compareAudits`, `earlierFailureOf`, `flipsOf`, `FLIP_AUDITS`, `confirmationOf`, `Comparability`, `scoreDeltaOf`, new `distinctObservations`. `server/compare-data.ts`: `cellRunsOf` (select `run.reused_from_run_id`, `run.finished_at`), `historyOf` and the `older` query in `comparisonOf` (`HISTORY_AUDITS`, new `HISTORY_SCAN`), `confirmationsOf` (`observedFloor`), new `witnessesOf`, `comparisonStampOf`, `tagSideOf`, `diffTags` and `tagDiffOf`. `server/recheck-data.ts` (cell labels only), `lib/compare-text.ts`, `components/compare/{summary,notices,findings-table,change-sheet}.tsx`, and the report's `changes` section in `lib/report-projection.ts` (new reasons, confirmation date, validators). Readers outside Compare (Overview, Findings, matrix, Hits) are unchanged: they read one audit.
9. **Estimate and progress count only new captures.** The preview and the audit page's estimate use the work units (a journey run counts 1 plus its steps, a cross-host run 2, as `runBreakdown`) of runs whose `reuse_plan` is null (recaptured runs **and** ordinary-path runs: both ask the engine); a reused run costs a few hundred milliseconds and counts 0. Progress ("12 of 28 runs") counts every run; a reused run is finished once its `persist` commits. A fallback adds that run's work back, so the estimate can grow by that much, and the existing "estimate holds until a unit finishes" rule applies. The workflow marks the audit `running` at its first step when it has a reused run. (r3) "Zero recaptures" is not "zero browser work": the preview carries `browserRuns` = recaptured + ordinary-path runs, and the start-page preflight, the estimate and every claim that no engine is needed read that number, never `recapture`. A fallback can add browser work to a retry that planned none, so "no browser" is a plan, not a promise.
10. **Admission is unchanged.** Reused runs never call `admit`, `confirm` or `release`; recaptured runs use `grantFor` and `capture` exactly as today, with the audit id as key, in the same FIFO. The reuse pass runs first (no engine), then the capture loop.
11. **Report and CSV disclose it.** `ReportModel` version 7 adds `captureSpan`: `{ from, to, reusedRuns, totalRuns, reusedFromDate }`.
    - `from` and `to` are the min and max `finished_at` of target runs that **own a capture** (`capture_key is not null`; runs settled by `fail-<n>` have a `finished_at` but no capture and are excluded), as UTC calendar days (`YYYY-MM-DD`); `reusedFromDate` is the UTC day of `audit.retry_of_at`.
    - Durable wording, built only in `lib/report-projection.ts`: "Captured between 28 Oct 2026 and 29 Oct 2026 (UTC). 24 of 28 results were reused from the audit of 28 Oct 2026 and judged by the checks of this report." No "today", "yesterday" or relative dates. Without reuse, one line with the range.
    - `REPORT_MODEL_VERSION` becomes 7, and the accepted versions are written out as `Schema.Literals([1, 2, 3, 4, 5, 6, 7])`, so 6 is explicitly kept. `UPGRADES[6]` sets `captureSpan: null`, rendered as "Not recorded in this version". Every leaf of `captureSpan` (and the null path of the object) gets a validator in `LEAF_VALIDATORS`, which lives in `lib/report-projection.ts`. The frozen sample model in `lib/sample-report.ts` is edited by hand to `modelVersion: 7` with `captureSpan: null`.
    - CSV register: three columns "Captures from", "Captures to" (ISO day) and "Reused results" (count), on ordinary and Fixed rows alike; every cell goes through `csvCell` inside `csvFile`. No capture text or message column.
12. **Who, when.** Any member (as Re-run); `membership`, then the org check on the audit (another organization's id is a 404); a `mutation`. Eligible origin in v1: a `full` audit with status `complete` or `partial` that is evaluated (has check results), on a non-archived site. A `failed` or unevaluated origin is excluded in v1 (it cannot be a valid baseline and has little to reuse); Re-run is the remedy. (Task 0, owner decision) Wholly unevaluated origins stay out of v1: the feature recovers an **evaluated partial audit**. An audit in which every run failed `PersistFailure` has no check results, is not eligible, and its remedy is Re-run; this is not a database-outage tool. Within an eligible origin, a retry is **eligible** when at least one run is recapturable or is a persistence-only repair (`PersistFailure`). (r3) Eligibility is not browser work: the preview reports `browserRuns` (recaptured + ordinary-path runs). Only when `browserRuns` is 0 does the retry run no browser (barring a fallback), finish in seconds, skip the start-page preflight and use the label "Save results again"; otherwise the label is "Retry n runs" with n = recaptured + persistence-only runs, and the dialog says that refused runs will be sent to the engine again. When a newer full audit of the site exists the dialog warns ("A newer audit from 29 Oct exists. This retry reuses captures from 28 Oct, so it cannot show changes since then; Re-run checks the site again.") and does not block; Decision 8 is what makes that safe.

**1. Two separate things: the heartbeat and the fence (r6, r7).** *The heartbeat* is a short transaction of its own, **committed before the attempt does anything else** (before any storage read, decoding or other work), at the start of every actual attempt of every step (a replayed, cached successful result runs no callback and writes nothing): `beat(auditId)`, the statement below on its own. It commits independently, so a later failure of the attempt cannot roll it back and a failure before the mutating transaction still leaves a record. It is itself fenced: zero rows means the audit is no longer active, the step returns `Fenced` at once and does nothing else. *The fence* is the same statement as the **first statement of every mutating transaction**, which is what serialises the transaction with settlement. **The audit row is the fence.** A transaction of the `Audit` workflow that writes anything about the audit starts with one statement on the audit row, before it touches any run, hit, check result or finding:

```sql
update audit set progress_at = now()
 where id = :auditId and org_id = :orgId and status in ('queued', 'running')
returning id
```

In the mutating transaction it is the fence (its `progress_at` write is incidental); the update takes the audit row lock (`FOR NO KEY UPDATE`, which does not conflict with the `FOR KEY SHARE` that `createAudit` and `rerunBaseline` take on a baseline), holds it to the end of the transaction, and returns no row when the audit is no longer active. Zero rows means **fenced**: the transaction writes nothing, rolls back, and the step returns a terminal `Fenced` outcome (a successful step result, never a thrown error, so Cloudflare does not retry it); the workflow loop treats `Fenced` as stop and returns `{ status: "fenced" }` without further steps. The transactions that begin this way: `start`, `capture-<n>` (the run-row update that stores the keys; the objects are written to R2 before it, outside the transaction, and an object written after a fence is an unreferenced orphan under the run's own prefix), `persist-<n>`, `fail-<n>`, `requeue-<n>`, `finish`, and later `reuse-<n>`. Steps with no database write (`admit-<n>`, which calls the gate, and each wait) run only the heartbeat transaction at attempt start and stop on `Fenced`. A `Fenced` capture attempt still returns its engine grant with the token-matched `release` (a terminated instance may leave a grant until its lease expires, which is accepted). Because the statement comes first in every transaction, the lock order is **audit, then runs, hits, pushes, check results, findings** everywhere (no transaction takes a run row and then waits for the audit), and the workflow transactions never lock client or site, so settlement's order (client, site, audit, then finer) has no cycle with them.

**2. Settlement serialises with every step.** `settleAudit` (section 6) locks the audit row `for update` first (after `for key share` on client and site, as AGENTS.md orders them). A workflow transaction that holds the audit lock finishes first and settlement sees all of its writes; a workflow transaction that starts after settlement finds the audit no longer active, is fenced and writes nothing. So a settled audit **cannot change again**, which is what the immutability of terminal witnesses, publications and the freed cap slot rely on. This withdraws r5's "its `finish` heals the audit": a late workflow ends fenced. After the transaction commits, settlement calls `Jobs.terminate("audit", id)` (a new method; best effort, outside the transaction, failure logged only) so a still-live instance stops quickly instead of retrying until it is fenced.

**3. Heartbeat and the real worst-case silence (r6, r7).** `audit.progress_at timestamptz` (nullable; one small migration, this task's own) is written by the committed heartbeat transaction of section 1, so **every actual attempt of every step records it at its start, retries and attempts that later fail included**. The longest legitimate gap between two records is therefore one retry delay plus the part of an attempt before it fails or times out: with `STEP = { retries: { limit: 8, delay: 15 s, exponential }, timeout: 4 minutes }` (`Audit.ts:84`) the largest delay is 15 s * 2^7 = 1920 s = 32 min, and an attempt runs at most 4 min, so **36 min**; the other steps have smaller delays (`CAPTURE_STEP` 5 s constant, `ADMIT_STEP` 2 s * 2^4) and the engine busy backoff is at most 240 s in all. (Without a per-attempt heartbeat the silence would be the sum over an exhausted step, 63.75 min of delays plus nine 4-minute attempts = 99.75 min, and about 199.5 min for a failing `persist` followed by a failing `fail`.) **`STALE_AFTER` = 90 minutes**, 2.5 times the bound. Correctness does not rest on this number: the fence makes a wrong settlement harmless to the data (the live workflow ends fenced), the number only decides when an unreachable workflow is given up. If the database itself is unreachable, neither the workflow nor a reconciler can write; when it returns, either order is safe.

**4. `launchAudit`, corrected.** `Jobs.start` is idempotent by instance id. After any failed `start` the audit is left `queued` and the error is logged: **no status lookup, no `failed`**. A `start` error whose text is the duplicate-id error (`instance.already_exists`) only means the instance exists and sets `workflow_id` (a pointer equal to the audit id, harmless if wrong). All updates are conditional on the current row (`... where id = :id and status = 'queued' and workflow_id is null`).

**5. `reconcileActive(orgId)`** (`server/audit-reconcile.ts`), run by `createAudit` before its transaction (outside it: it calls `Jobs`; callers have already passed `membership`) and by the mutation below.    2. **Authoritative terminal status:** `workflow_id` set, `Jobs.status` **read successfully** and equal to `errored` or `terminated`, or `complete` while the row is still active → `settleAudit`.    3. **Orphan:** `queued`, `workflow_id` null, created more than 5 minutes ago, `progress_at` null: call `launchAudit(auditId)` again (create with the fixed id; a duplicate means it exists and is left alone).    4. Otherwise nothing: a healthy `running` workflow however slow is left alone.

## Alternatives considered (short)

- **Retry in place** (first version of this plan): rejected after review r1.

### 6. Decisions the findings put in doubt

- **Persistence-only retry (Decisions 2, 12)** only helps when part of the audit persisted. Owner decision (r3): wholly unevaluated origins stay out of v1; the feature is recovery of an evaluated partial audit.
- **Reuse chronology (Decision 8)** was incomplete: D against C reports a false Fixed (fixed by the superseded class, accepted by the owner).
- **"Retry n runs" for timeouts** will often fail again for genuinely heavy pages (CNN, The Verge time out on the engine every time); the count is honest, the promise in the dialog must not be.
- **Storage duplication (Open question 1)**: real captures are far below the 10 MiB ceiling (mean 286 KB, max 773 KB per run in ten real captures); duplication looks cheap enough.
- **Ordinary path (Decision 2)**: an unresolvable host is refused by the engine, so "refused again at once" is true only while the cause lasts; a transient resolver failure is retried only by Re-run or as a rider.
